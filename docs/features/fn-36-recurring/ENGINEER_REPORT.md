## Migration `0023_recurring.sql`

- New table `recurring_transactions` (FN-05-style row: `space_id` FK cascade, `seq`, `updated_at`, `deleted_at`,
  content-free tombstone). Columns per PRD plus `attention` (`limit`|`refs`|`member`, the "Perlu perhatian"
  reason). CHECKs: `type` in (expense, income); `status` in (active, paused, stopped); `attention` enum; content
  check (live row: amount 1…10^13, currency, wallet, category, `frequency`+`interval_day` 1–31 monthly / 1–7
  weekly, `start_on`, `next_run_on`, `end_on` ≥ `start_on`; tombstone: every content column null).
  `created_by_user_id` FK `users` ON DELETE SET NULL. Indexes: `(space_id, deleted_at)` and a partial
  `(space_id, next_run_on) WHERE status='active' AND deleted_at IS NULL` for the cron walk.
- `ALTER TABLE transactions ADD recurring_series_id text REFERENCES recurring_transactions(id)` plus index
  `(space_id, recurring_series_id)`. **No rebuild**: SQLite/D1 accept `ADD COLUMN … REFERENCES` when the column
  defaults to NULL, even with foreign keys enforced, so the FK is real and no trigger is needed. Generated by
  `drizzle-kit generate` (snapshot `meta/0023_snapshot.json`), header comment added. `transactions.recurrence`
  (FN-18 CSV free text) is untouched.
- Applied: fresh scratch DB (0000–0023 all ✅) and a scratch DB populated at 0022 (user, space, wallet, a
  transaction with FN-18 `recurrence='Bulanan'`) → only 0023 applied; before/after counts, `max(seq)` and
  `sum(updated_at)` identical, `recurring_series_id` null everywhere, `PRAGMA foreign_key_check` empty. (The demo
  seed added no rows there: it needs categories; the populated set is small.)

## Cron / queue design

- `workers/jobs/src/cron.ts`: `CURSOR_KEYS.recurring_check`, one more `walk` (round `all`, wrap) over
  `spacesWithDueSeries(today, after, 100)` on every open tick (`tickPlan().recurring`, 06–23 WIB, the existing
  hourly trigger; no new trigger, no new queue). Enqueues `{ type: 'recurring_check', spaceId }` (ids only).
- `src/lib/shared/jobs.ts`: new union member; `queue.ts` handler calls `deps.recurringCheck(spaceId)`; a throw
  → `retry()` → after `max_retries: 3` the existing DLQ (`financer-jobs-dlq`).
- `runDueSeries(db, spaceId, today, now)` (`src/lib/server/recurring/repo.ts`): pages due series by id, catches
  each up run by run while due, at most `MAX_INSTANCES_PER_RUN = 100` attempts per message; the next tick
  continues. Each attempt (`createDueInstance`) is one `db.batch`:
  1. `bumpSpaceSeq`;
  2. `insertTransactions` (unchanged write path, one optional `recurringSeriesId` field added to `NewTransaction`)
     with `source 'manual'`, dedupe key `recurring:<series>:<WIB date>`, guarded by: series still active, not
     deleted, `next_run_on = runOn`, `updated_at` as read, and `NOT EXISTS` any transaction (tombstones included)
     with that dedupe key; `insertTransactions` itself re-checks the series member (`isLiveMember`), wallet,
     category and `MAX_TRANSACTIONS_PER_SPACE`;
  3. advance `next_run_on` to the following run (status → stopped past `end_on`), only while still due on that
     date and a transaction with that key exists.
  Redelivery / overlapping ticks: the second attempt finds the date advanced → `changed`, nothing written;
  `transactions_dedupe_uq` stands behind the guard. A deleted instance → `advanced` (never recreated).
- Refused insert → reason computed (`limit` / `member` / `refs`) and the series flagged in a guarded update.
  `limit` stays due and is retried every tick (AC14); `refs`/`member` are skipped by the cron until the user
  edits or resumes the series, which clears the flag, takes the series over (`created_by_user_id` = editor) and
  restarts from today (no backfill).
- Schedule math: `src/lib/shared/recurring.ts` wraps FN-26's `nextChargeOn` (same clamping, one implementation;
  a test asserts equality). Placed in `shared` (not `server/recurring/schedule.ts` as the PRD sketched) because
  the series pages render the schedule label client-side too.

## Cycle 2 — red team M1, L1, L2

### Limits confirmed (official pages, fetched 2026-10-08)

- https://developers.cloudflare.com/d1/platform/limits/ (last updated 2026-04-21): "Queries per Worker invocation:
  1000 (Workers Paid) / 50 (Free)"; max bound parameters per query 100; per-statement limits apply to every
  statement of a `db.batch()`.
- https://developers.cloudflare.com/workers/platform/limits/#subrequests (modified 2026-09-05): subrequests per
  invocation 50 (Free) / 10,000 (Paid); subrequests to internal services 1,000 (Free) / the configured limit (Paid).
- https://developers.cloudflare.com/queues/platform/limits/: consumer batch up to 100 messages (ours: 10),
  consumer wall time 15 min, default CPU 30 s per invocation.
- Design target: the stricter D1 figure, 1,000 per invocation, counting every statement of a batch as a query
  (conservative). The Free plan's 50 is not a target (one ordinary batch of jobs already needs more).

### M1 (bounded D1 work per invocation)

- `RECURRING_STATEMENTS_PER_INVOCATION = 300` (`src/lib/server/recurring/repo.ts`): one `D1Budget` per queue
  invocation (`workers/jobs/src/index.ts`), shared by every `recurring_check` of the batch; each call takes its
  worst-case cost before it runs, so recurring work never passes 300 statements and >= 700 stay for the rest.
- `handleBatch` runs `recurring_check` messages after every other message of the batch; a check whose work did
  not fit (budget or the 100-instance cap) is acked and continued by one fresh message with the same date (never
  counts toward the DLQ); a thrown D1 error retries only that message.
- `runDueSeries`: one select reads the due page plus the space's live row count; instances planned locally
  (`dueRuns`, chained `updated_at`) and attempted 20 per `db.batch` (`attemptInstances`); refused ones explained
  by one select and flagged by one batch. 100 instances: 6 calls / ~206 statements (was 201 calls / ~400).
- Flagged series: `refs`/`member` never read (1 select per space, tested); a space at MAX_TRANSACTIONS_PER_SPACE:
  1 select, plus once 1 batch flagging all its series `limit` (tested: 2 calls / 3 statements, then 1 / 1).
- Per-user cap on shared spaces: not added. FN-03 makes several spaces a Pro feature with no number; the
  per-invocation budget already bounds the effect. Follow-up for the owner if a cap is wanted.

### L1

- `recurring_check` carries `date` (the tick's WIB day, `plan.today`); the handler uses it, clamped to the
  processing WIB date, so a delayed message never creates the next day's rows. Message without `date` refused.
