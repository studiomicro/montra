# FN-03 Spaces and sharing (Ruang) — PRD

Catalog entry: `docs/FEATURES.md` › FN-03. Phase: 0 — Foundation. Tracker: `docs/TASKS.md` › Phase 0 ›
"FN-03 Spaces and sharing. Risk: Large." Risk tier: **Large** (new concurrency-sensitive tables, the one
space-access helper every later space-scoped feature (FN-04+) must call, and an extension of
`src/hooks.server.ts` that runs on every `(app)` request).

Owner decisions already fixed for this pass (2026-10-07, do not re-litigate): storage is server-first in D1,
no guest mode/local-first sync this phase (FN-02 later adds the sync cursor and `space_seq`); FN-01 (built in
parallel, `docs/features/fn-01-accounts/PRD.md`) creates `spaces` and `space_members` and, at sign-up, the
personal space + owner membership — FN-03 extends those tables, it does not redefine them; invitations are
link-only with a 7-day expiry, shared by the user themselves (no e-mail-sending provider yet); route is
`/ruang` per `CLAUDE.md` › UI and routes.

## Goal

Every shared financial feature in Phases 1+ (wallets, transactions, budgets, goals) is scoped to a `space_id`,
and CLAUDE.md is explicit that "a hidden button is not authorization" — so one shared, well-tested gate must
decide who may read or write a space's rows before any of those features exist. FN-03 is that gate plus the
thin slice of UI the main journey needs to use it: a household manager creates one shared space, sends a link,
a partner joins from their own account, both see the same wallets and budgets once FN-04+ ship, and the owner
can remove someone (or a member can leave) without losing their own personal space. Without FN-03, FN-04
onward have no safe way to ask "does this user get to see this row?" and the main journey's last step
("invite a family member") has no feature behind it.

## Scope

- **Migration `0002`** (`migrations/0002_*.sql`, generated by `drizzle-kit generate`, applied only through
  `npm run db:migrate:local`; the number assumes FN-01's `0001_*.sql` lands first — see Prerequisites if build
  order flips): two new tables, `space_invites` and `audit_events` (columns below); no changes to FN-01's
  `spaces` / `space_members` column shapes, only new rows in them.
- **`src/lib/server/spaces/access.ts`** (new) — the space-access helper (the main deliverable): membership
  lookup, role check, current-space resolution from the `space` cookie with fallback to the personal space,
  `MAX_SPACE_MEMBERS = 5`.
- **`src/lib/server/spaces/invites.ts`** (new) — token generation and hashing, create/revoke/accept logic,
  the single-active-link policy, the 5-member cap enforced as one guarded statement.
- **`src/lib/server/spaces/audit.ts`** (new) — `recordAuditEvent` for the five sharing actions below.
- **`src/hooks.server.ts`** — extend (after FN-01 adds `locals.user`) to resolve `locals.space` (id, kind,
  role) from the `space` cookie on every `(app)` request, via the access helper, falling back to the user's
  personal space when the cookie is missing, invalid, or no longer a membership.
- **Routes**, all under `src/routes/(app)/ruang/` (replaces the current `[stub=stub]` placeholder for this one
  slug):
  - `/ruang` — list of spaces the signed-in user belongs to (personal first, then shared, each with role and
    a "current" marker); "Buat ruang bersama" entry point; a `switchSpace` action.
  - `/ruang/baru` — create-shared-space form (name only); on submit, becomes the new current space.
  - `/ruang/[id]` — space detail: member list with role (Pemilik / Anggota); for the owner, the active invite
    link (create, copy, revoke, regenerate) and a remove-member action per non-owner member; for a member, a
    "Keluar dari ruang" action. Guarded by the access helper on every load and action, independent of
    `locals.space`.
  - `/ruang/undangan/[token]` — accept-invite page: resolves the invite by its token hash; if signed out,
    redirects to `/masuk?next=/ruang/undangan/<token>`; shows the space name and an "accept" action that joins
    the space (subject to the 5-member cap), sets it as the current space, and redirects to `/`.
- **i18n:** every new Indonesian phrase added to `src/lib/shared/i18n.ts` call sites with an English entry in
  `src/lib/shared/i18n-en.ts` (`Ruang` → `Spaces` already exists, `src/lib/shared/i18n-en.ts:12`).
- **UI states:** loading (list/detail skeletons), empty (`/ruang` with only the personal space — no shared
  spaces yet), error (load failure with retry), saving (button disabled/spinner on every action), success
  (shown only once the server confirms: new space created, invite created/revoked, member removed, left,
  accepted).
- **`src/params/stub.ts`** — remove `'ruang'` from the stub `SLUGS` set (`src/params/stub.ts:1`), the same way
  FN-01 removes `/daftar`/`/masuk`/`/pengaturan/akun`.

## Out of scope

- Several shared spaces per user and any plan gating on them (comparable apps make this Pro-only; FN-30 billing does
  not exist yet — see Owner decision C).
- Owner leaving a shared space, transferring ownership, or deleting a shared space outright (only member
  remove-by-owner and member self-leave ship this pass — see Owner decision D).
- A custom space avatar/photo upload; `/ruang` and Beranda show initials or an icon only, no R2 upload.
- Inviting to the personal space (personal spaces are never `kind = 'shared'` and never show an invite UI).
- Invite by code (only by link, per the owner decision already fixed); any QR code for the link.
- Any UI that reads `audit_events` back (the table is written this pass, not displayed; FN-31 or a later admin
  view may read it).
- The per-space change log, sync cursor, and `space_seq` column (FN-02); two-device sync of membership changes.
- Wallets, transactions, budgets, goals actually being scoped by `space_id` in their own tables/queries — that
  is FN-04+'s job, done by calling this feature's helper, not by this feature.
- Push/e-mail notification of "you were invited" or "you were removed" (no notification system exists before
  FN-13/FN-24).

## Acceptance criteria

**The space-access helper (the FN-04+ contract)**

1. Given `event.locals.user.id` and any `spaceId` string, when the helper (`requireSpaceAccess(db, userId,
   spaceId)`) runs, then it returns `{ space: { id, kind, name }, role: 'owner' | 'member' }` for an existing
   membership, or throws the SvelteKit `error(404, …)` with one fixed, generic body for every other case: the
   space does not exist, it exists but the user has no membership row, or the membership row is a tombstone —
   all three produce the same status code, body shape, and are backed by one query so there is no timing tell
   between "space missing" and "space exists, not yours" (checklist › Access and privacy › "One access rule").
2. Given the same inputs plus a required role (`requireSpaceAccess(db, userId, spaceId, { role: 'owner' })`),
   when the caller's role does not match, then it throws `error(403, …)` — not 404, because the caller already
   has a membership and therefore already knows the space exists; this is the only branch allowed to reveal
   more than "not found".
3. Given a load function or action anywhere in this feature that receives a space id from a route param or a
   form field, when it runs, then it calls the helper with that id — never trusts `event.locals.space` for an
   id supplied by the request itself (`locals.space` is only the *default* current space for routes that do
   not take one as a param).
4. Given a request with no `space` cookie, an invalid value, or a value naming a space the user no longer
   belongs to, when `hooks.server.ts` resolves `locals.space`, then it falls back to the user's personal space
   without erroring the request.

**Create a shared space**

5. Given a signed-in user at `/ruang/baru`, when they submit a non-empty name, then one `spaces` row
   (`kind = 'shared'`), one `space_members` row (`role = 'owner'`), and one `audit_events` row
   (`action = 'space_created'`) are written in one `db.batch`, the `space` cookie is set to the new space id,
   and the response redirects to `/ruang/<id>`.
6. Given the name field contains control or zero-width characters or exceeds the stored length cap, when
   submitted, then they are stripped/capped before storage (checklist › Access and privacy › "Untrusted text"),
   matching FN-01's treatment of the sign-up name field.
7. Given JavaScript is disabled, when the create-space form is submitted, then it still works as a normal form
   POST.

**Invite link (owner only)**

8. Given the owner of a shared space on `/ruang/[id]` with no active invite, when they create one, then a
   `space_invites` row is written with a hashed token, `expires_at` = now + 7 days, and the full link (shown
   once, including the raw token) is rendered with a copy control; a second, independent read of the same page
   cannot recover the raw token, only that an active invite exists and when it expires.
9. Given an owner creates a new invite while one is already active, then the previous invite's row is
   tombstoned (`deleted_at` set) in the same write that creates the new one — at most one usable link per
   space at a time.
10. Given a member (not the owner) attempts the create/revoke-invite or remove-member action on their own
    space, when the action runs, then it is refused with `error(403, …)` per criterion 2, and no row changes.
11. Given the owner revokes the active invite, when revoked, then its row is tombstoned, an `audit_events` row
    (`action = 'invite_revoked'`) is written, and the previously copied link no longer accepts a join
    (criterion 14).
12. Given two concurrent "create invite" submissions from the owner (pre-handoff two-tabs probe), when they
    race, then exactly one invite ends up active (the other either tombstones itself or is rejected), never two
    simultaneously valid links.

**Accept an invite**

13. Given a signed-out visitor opens `/ruang/undangan/<token>` for a valid, unexpired, unrevoked invite, when
    the page loads, then they are redirected to `/masuk?next=/ruang/undangan/<token>` and, after signing in,
    return to the same accept page.
14. Given a signed-in user opens an invite link that is invalid, expired, or revoked, when the page loads, then
    it shows one generic "Tautan tidak ditemukan atau sudah tidak berlaku" (and English) message — the three
    cases are not distinguished in the response, so a guessed or reused token gives no extra information
    (checklist › Access and privacy › "One access rule").
15. Given a signed-in user opens a valid invite for a space that already has `MAX_SPACE_MEMBERS` (5) members,
    when the page loads, then it shows "Ruang ini sudah penuh" (and English) and the accept action is
    unavailable; no row is written.
16. Given a signed-in user who is already a member of that space opens the invite, when they land on the
    accept page, then it behaves idempotently: no duplicate `space_members` row, no duplicate audit row, and
    the action simply sets the space as current and redirects to `/`.
17. Given a signed-in, not-yet-a-member user accepts a valid invite under the 5-member cap, when the action
    runs, then one `space_members` row (`role = 'member'`) and one `audit_events` row
    (`action = 'member_joined'`) are written in one guarded statement that re-checks the member count inside
    the same write (checklist › Data access › "Concurrent writes"), the `space` cookie is set to the space id,
    and the response redirects to `/`.
18. Given 20 concurrent accept submissions for the same invite when the space has exactly 4 members (one slot
    left — pre-handoff concurrency probe), when they race, then exactly one succeeds and the other 19 each see
    the "Ruang ini sudah penuh" outcome, never a 6th row and never a 500.
19. Given a request to `/ruang/undangan/<token>` where `<token>` is any string (including one far outside the
    stored format), when it loads, then the response is the same "not found" shape as an expired token, never
    a 500 or a different error page.

**Space switcher**

20. Given a signed-in user with at least one shared space, when they choose it from `/ruang`'s list
    (`switchSpace` action), then the helper re-validates the membership before the `space` cookie is updated —
    submitting an arbitrary id the user is not a member of is refused (`error(403, …)` or `404` per criteria
    1–2) and the cookie is left unchanged.
21. Given a reload after switching, when any `(app)` page loads, then `locals.space` still reflects the chosen
    space (persisted state survives reload, per the cookie, re-validated each request).

**Member list and leaving**

22. Given any member on `/ruang/[id]`, when the page loads, then the member list shows each person's role as
    "Pemilik" or "Anggota" (English: Owner/Member), with a loading skeleton while the load runs and a retry
    state on failure.
23. Given the owner removes a non-owner member, when the action runs, then that `space_members` row is
    tombstoned, an `audit_events` row (`action = 'member_removed'`, `target_user_id` set) is written, and if
    the removed member's own `space` cookie currently names that space, their *next* request falls back to
    their personal space per criterion 4 (no error shown to them, no silent continued access).
24. Given the owner attempts to remove themselves, when the action runs, then it is refused — there is no
    owner-self-removal or owner-leave path in this pass (Owner decision D); the UI does not render a "Keluar"
    control for the owner on a shared space.
25. Given a non-owner member chooses "Keluar dari ruang", when the action runs, then their `space_members` row
    is tombstoned, an `audit_events` row (`action = 'member_left'`) is written, their `space` cookie resets to
    their personal space, and they are redirected to `/ruang`.
26. Given a user who is not a member of a space (including a just-removed member re-requesting the old URL),
    when they request `/ruang/[id]` or any action on it, then they get the uniform 404 of criterion 1, never a
    page that reveals the space's name or member list.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

27. Every load function and form action added by this feature that touches a specific space id calls
    `requireSpaceAccess` (criteria 1–3) — no route in this feature trusts a client-supplied role or space id
    without it.
28. Every Indonesian phrase added for this feature has an English entry in `i18n-en.ts`; `npm run test`
    (`src/lib/shared/i18n.test.ts`) fails if one is missing.
29. `{#each}` lists (space list, member list) are keyed by the space id / membership id, never by name.
30. Every form body on `/ruang/baru`, `/ruang/[id]`'s actions, and the accept action is read within a size cap
    and answers 400/415, never 500, on a malformed or oversized body (reuses FN-01's `src/lib/server/forms.ts`
    guard rather than a second one).
31. Invite expiry and audit timestamps shown in the UI are converted to WIB from the stored UTC integer (no
    amounts exist in this feature, so no money-arithmetic criterion applies, per `CLAUDE.md` › UI and routes).
32. User-facing error text never contains a file path, stack trace, session id, row id, or raw token.
33. Focus returns correctly after the invite-link copy confirmation and any confirm dialog (remove/leave);
    touch targets ≥ 44 px; WCAG AA contrast in both themes (FN-00 token system, no new colours).
34. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression
    test (especially criteria 1, 2, 12, 14, 18, 20, 24, 26) is shown failing on the unfixed code first
    (checklist › Tests › "Fail-before proof").

## Owner decisions

**Answered by the owner 2026-10-08: accept every proposed default below as written.**


The following are genuinely open for this pass (distinct from the decisions already fixed above); proposed
defaults are used unless the owner overrides them before build:

- **A. Invite token storage.** *Proposed default:* store only a hash of the invite token (reusing FN-01's
  session-token hash function), the same way session tokens are stored — the raw link is shown once at
  creation and must be copied then. *Trade-off:* if the owner navigates away without copying, they must revoke
  and generate a new link rather than re-reading the old one; the alternative (storing the raw token in
  cleartext, re-copyable any time) is simpler UX but weaker if the D1 row is ever exposed.
- **B. One active invite link per space, or several at once.** *Proposed default:* exactly one active link;
  creating a new one revokes the previous (criterion 9). *Trade-off:* an owner cannot keep two differently-
  scoped links alive at once (e.g., one for a partner, one for a sibling, revoked independently) — if the
  owner wants that, a later pass would need to drop the single-link policy and add per-invite revoke-only UI
  (already a separate `space_invites` row per link, so the schema does not block it later).
- **C. Shared-space creation limit per user.** Comparable apps gate multiple/shared spaces behind a Pro plan; FN-30
  (billing) does not exist yet. *Proposed default:* no cap in this pass — any signed-in user may create any
  number of shared spaces for free, revisited when FN-30 ships plan gating. *Trade-off:* until then, the
  usual "Pro feature" is free for everyone, which the owner may want flagged in a future plans
  rollout rather than silently grandfathered.
- **D. Owner leaving or deleting a shared space.** *Proposed default:* out of scope this pass — an owner can
  only remove members (down to just themselves) and cannot leave or delete the space; dissolving a shared
  space entirely has no path yet. *Trade-off:* an owner who wants to stop sharing must remove every other
  member one at a time; there is no single "disband this space" action until a later pass adds one.
- **E. `audit_events` table: add now or defer.** `docs/PRD.md` § 7 already lists "audit log for sharing […]"
  as a non-functional requirement, and the table is already named in `docs/ARCHITECTURE.md`'s data model.
  *Proposed default:* add it now, in this feature's migration, logging the five sharing actions listed above,
  with no reader UI yet. *Trade-off:* the schema (and its retention policy, left to FN-31) is committed before
  anything displays it; if the owner would rather wait until there is a viewer, the six acceptance criteria
  that check `audit_events` rows (5, 9, 11, 17, 23, 25) would be dropped and the table deferred to whichever
  feature first reads it.
