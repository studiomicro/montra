# FN-04 Wallets (Dompet) — PRD

Catalog entry: `docs/FEATURES.md` › FN-04. Phase: 1 — Core ledger. Tracker: `docs/TASKS.md` › Phase 1 ›
"FN-04 Wallets · FN-05 Transactions and history · …" (FN-04 is the first slice of that combined line). Risk
tier: **Medium** (new table + migration, new CRUD routes, no auth/session subsystem changes, balance math is a
single sum with no transactions table to join against yet).

Owner decisions already fixed for this pass (2026-10-07, do not re-litigate): server-first in D1, signed-in only
(no guest mode this pass); every wallet row belongs to one space and every query goes through the FN-03
space-access helper; migration number `0001` is reserved by FN-01 (`docs/features/fn-01-accounts/PRD.md`) — FN-04's
migration is **`0002`** unless FN-03 also lands a migration first, in which case FN-04 is `0003`; renumber at
merge if the actual merge order differs. Money is integer `amount_minor` + ISO 4217 `currency`, display only
through `src/lib/shared/money-format.ts`. Wallets UI lives on the **Kekayaan tab** (`/kekayaan`), not under
`/pengaturan` — see Scope rationale and Owner decision C.

## Goal

Every capture path (manual entry first, then voice, receipt, statement, Gmail in later phases) has to land in
some wallet, and the main journey's step 2 is literally "add a wallet" (`CLAUDE.md` › Product boundaries).
Without FN-04 there is nowhere for FN-05's transactions to point, no favourite wallet for FN-04's own matching
rule or FN-14/FN-19's wallet-word matching to resolve against, and `/kekayaan` has nothing to show. FN-04 gives
the user a short, honest list of their cash, bank, e-wallet and card wallets with a balance each, lets them add
one in under a minute, and defines the balance contract (`opening_balance_minor` now, `+ Σ transactions` once
FN-05 ships) so the next feature plugs in without a schema change.

## Scope

- **Migration `0002`** (`migrations/0002_wallets.sql`, generated by `drizzle-kit generate` from an added
  `wallets` table in `src/lib/server/db/schema.ts`, applied only through `npm run db:migrate:local`): one table,
  `wallets` (columns below under Architecture notes).
- **`src/lib/server/wallets/`** (new):
  - `repo.ts` — `listWallets(db, spaceId, { includeArchived })`, `getWallet(db, spaceId, walletId)`,
    `createWallet(db, spaceId, input)`, `updateWallet(db, spaceId, walletId, input, expectedUpdatedAt)`,
    `archiveWallet(db, spaceId, walletId, expectedUpdatedAt)`, `setFavourite(db, spaceId, walletId)`. Every
    function takes `spaceId` from the caller (already authorized by the space-access helper) and filters
    `deleted_at IS NULL` by default.
  - `balance.ts` — `walletBalanceMinor(wallet, transactionsSumMinor = 0)` → `wallet.openingBalanceMinor +
    transactionsSumMinor`; the **balance contract** FN-05 implements against (see Architecture notes). Until
    FN-05 ships, every call site passes `0` for the sum, so a wallet's shown balance is exactly its opening
    balance.
  - `validation.ts` — zod schema for the add/edit form: `name` (1–60 chars, control/zero-width stripped per
    checklist › Access and privacy), `type` (`tunai` | `bank` | `e_wallet` | `kartu_kredit` | `lainnya`),
    `currency` (ISO 4217, default `IDR`), `openingBalanceMinor` (integer, via `digitsToMinor`, may be negative
    for a credit-card wallet carrying a balance), `isFavourite` (boolean), `lastFour` (optional, exactly 4
    digits, never more than the last 4 — reject input that looks like a longer account/card number instead of
    silently truncating, per checklist › Access and privacy › Masking).
- **Routes** (all under `(app)`, session-gated by FN-01's `hooks.server.ts`, space-scoped by the FN-03 helper):
  - `src/routes/(app)/kekayaan/+page.server.ts` (new) — `load` lists the current space's active wallets with
    balances (balance = opening balance only, this pass) ordered favourite-first then by `created_at`; actions
    `createWallet`, `updateWallet`, `archiveWallet`, `setFavourite`.
  - `src/routes/(app)/kekayaan/+page.svelte` (replaces the current stub, `src/routes/(app)/kekayaan/+page.svelte:1-12`)
    — a "Dompet" grouped list (one `GroupRow` per wallet: name, type chip, masked last-4 if set, balance right,
    favourite star) plus an "+ Tambah dompet" row that opens a `Sheet` with the add/edit form; archived wallets
    hidden behind a "Lihat yang diarsipkan" toggle inside the same screen (no separate route this pass).
  - No `/pengaturan/dompet` route this pass — see Owner decision C.
- **i18n:** every new Indonesian phrase (wallet type labels, form fields, empty/error/success copy) added to
  `src/lib/shared/i18n.ts` call sites via `tr()`/`trf()`, with an English entry in `src/lib/shared/i18n-en.ts`;
  the existing coverage test (`src/lib/shared/i18n.test.ts`) fails the build if one is missing.
- **UI states:** loading (skeleton `GroupRow`s while `load` runs), empty (`EmptyState` — "Belum ada dompet. Tambah
  satu untuk mulai mencatat." + "Tambah dompet" action, replacing the current placeholder copy at
  `src/routes/(app)/kekayaan/+page.svelte:11`), error (inline banner with retry on a failed load or action),
  saving (submit button disabled + spinner while the form action runs), success (the sheet closes and the list
  refreshes only after the server confirms the write — no optimistic row).
- **UI kit reuse:** `GroupList`/`GroupRow`, `Chip` (wallet type), `Segmented` (type picker in the form), `Badge`
  (favourite), `TextInput`, `AmountInput` (opening balance, using `amountDigits`/`digitsToMinor` from
  `src/lib/shared/amount-input.ts`), `Sheet` (add/edit), `Button`, `EmptyState` — all from `src/lib/ui/kit/` and
  `src/lib/ui/shell/` per the owner's FN-00 Task 10 delivery; FN-04 does not build any of these primitives itself,
  only wallet-specific composition.

## Out of scope

- The `transactions` table and any real balance beyond opening balance (FN-05); `walletBalanceMinor` is written
  now so FN-05 only needs to pass a real sum, not change the function's shape.
- Wallet matching from captured text ("GoPay" → e-wallet, "kartu kredit" → card wallet) — that is FN-14/FN-19/FN-16
  consuming FN-04's `name`/`type` columns, not built here.
- Transfers between own wallets (needs `transactions`, FN-05).
- Institution logo list (BCA, Mandiri, GoPay, …) — `type` + free-text `name` only this pass; a `logo_key` column
  can be added without breaking this schema later.
- Hard delete of a wallet — archive (soft delete, tombstone) only, per `CLAUDE.md` › Data and runtime
  conventions.
- A separate `/pengaturan/dompet` settings screen (Owner decision C — Kekayaan tab only this pass).
- Investasi as a wallet-adjacent category group (`docs/FEATURES.md` FN-04 "Mirror" note) — that belongs to
  FN-25 Net worth; FN-04's `type` enum has no `investasi` value this pass.
- Sync (IndexedDB, IDB-first) — out of scope per the storage decision; `seq` exists in the schema for later sync
  but nothing reads or writes it outside the server this pass.
- Reordering wallets by drag, custom wallet icons/colours beyond the type chip's fixed colour.

## Acceptance criteria

**List (`/kekayaan`)**

1. Given a signed-in user with no wallets in the current space, when `/kekayaan` loads, then the empty state
   shows "Belum ada dompet. Tambah satu untuk mulai mencatat." (and English) with a "Tambah dompet" action, and no
   "Rp" figure is shown anywhere on the page.
2. Given a signed-in user with wallets in the current space, when `/kekayaan` loads, then every active
   (`deleted_at IS NULL`) wallet appears, favourite first, each row showing name, type label, masked last-4 (if
   set, exactly `•••• 1234`-style, never more than 4 digits revealed) and balance formatted with
   `formatMoney`/`formatMoneyCompact` (never hand-formatted).
3. Given the load is in flight, when the page first renders, then skeleton rows show in place of the list (no
   flash of the empty state before data arrives).
4. Given the load throws (D1 unavailable), when `/kekayaan` is requested, then an error state with a retry action
   renders — never an unhandled 500 page.
5. Given a wallet was archived in a previous session, when `/kekayaan` loads again without the "Lihat yang
   diarsipkan" toggle on, then it is not in the list; turning the toggle on shows it marked "Diarsipkan" with no
   edit/favourite controls, only "Pulihkan" (unarchive).

**Add (`createWallet` action)**

6. Given the add sheet with name, type, currency (default `IDR`), opening balance and optional last-4, when
   submitted with valid input, then a `wallets` row is created with the given fields, `space_id` set to the
   current space, `amount` stored as an integer `amount_minor` (via `digitsToMinor`, never `parseFloat`), the
   sheet closes, and the new wallet appears in the list without a page reload.
7. Given the same action, when the reload happens (full page refresh after save), then the new wallet is still
   present — persisted state survives reload, not just the in-memory store.
8. Given a name of 0 characters, or control/zero-width characters in the name, when submitted, then the action
   fails with a field error (`tr()`/English) and strips/caps the name before any further validation (checklist ›
   Access and privacy › Untrusted text); no row is written on a validation failure.
9. Given a `lastFour` value that is not exactly 4 digits (e.g. a pasted 16-digit card number), when submitted,
   then the action rejects it with a field error rather than silently truncating to 4 digits — the user must
   enter the last 4 only (checklist › Access and privacy › Masking: masking happens by validation, never by
   storing more and truncating on display).
10. Given this is the user's first wallet in the space, when it is created, then `is_favourite` is set `true`
    automatically (there is always exactly one favourite once at least one wallet exists); given a second wallet
    is created, then it defaults to not-favourite and the first wallet's favourite flag is untouched.
11. Given the "Jadikan favorit" action on any other wallet, when submitted, then that wallet becomes the
    favourite and the previously favourite wallet's flag is cleared in the same guarded write (one `db.batch`,
    never two separate writes that could race — checklist › Data access › "Concurrent writes").
12. Given JavaScript is disabled, when the add form is submitted, then it still works as a normal form POST
    (progressive enhancement, checklist › Tests › pre-handoff "No-JS forms").

**Edit (`updateWallet` action)**

13. Given an existing wallet opened for edit, when the user changes name, type, opening balance, favourite or
    last-4 and submits, then the row is updated, `updated_at` advances, and the list reflects the change after
    the server confirms (no optimistic update shown before confirmation).
14. Given two browser tabs open the same wallet for edit (pre-handoff "two tabs / stale forms" probe), when both
    submit with the same stale `updated_at`, then the second submission is refused with "Berubah sejak
    terakhir dimuat" (and English), never silently overwriting the first tab's write.
15. Given an edit changes the opening balance, when saved, then the shown balance recomputes immediately on
    reload to `openingBalanceMinor + 0` (no transactions table yet) with no stale cached figure.

**Archive (`archiveWallet` action, soft delete)**

16. Given a wallet with no transactions pointing at it (true for every wallet this pass, since FN-05 does not
    exist yet), when "Arsipkan" is submitted, then `deleted_at` is set (tombstone, content-free per
    `CLAUDE.md`), the `seq` column advances, and the wallet disappears from the default list view immediately
    after the server confirms.
17. Given the archived wallet was the favourite, when it is archived, then the favourite flag moves to another
    active wallet if one exists (oldest-created active wallet becomes favourite), or `is_favourite` is left
    `false` on every wallet if none remain — the UI never implies a favourite that does not exist.
18. Given an archived wallet, when "Pulihkan" is submitted, then `deleted_at` is cleared, `seq` advances again,
    and the wallet reappears in the default list — archiving is reversible this pass (no transactions can yet
    reference it, so there is no FN-05 "never recreate a deleted captured row" conflict to resolve).

**Balance contract (for FN-05 to build against)**

19. Given a wallet with `openingBalanceMinor = 2_500_000` (Rp 25.000,00 stored as minor units — i.e.
    `openingBalanceMinor` itself already carries the currency's exponent) and no transactions table yet, when its
    balance is computed, then `walletBalanceMinor(wallet, 0) === wallet.openingBalanceMinor` exactly, and the
    displayed figure equals `formatMoney(wallet.openingBalanceMinor, wallet.currency)` — the Beranda/Riwayat
    "totals reconcile" rule (checklist › Money and dates) has nothing to reconcile against yet, but the function
    signature (`wallet`, `transactionsSumMinor`) must not change when FN-05 starts passing a real sum.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

20. Every `+page.server.ts` load and action under `/kekayaan` resolves the current space through the FN-03
    space-access helper using `event.locals.user` — never a client-supplied `spaceId`; a request for a wallet id
    that exists in a different space, or does not exist at all, gets the identical not-found response (status,
    body, timing) — no existence oracle.
21. A pre-handoff cross-space probe (crawl every `/kekayaan` route and action as a non-member and as a removed
    member of the space that owns a given wallet id) returns nothing and never 200s.
22. A pre-handoff concurrency probe (20 concurrent `setFavourite` submissions across two wallets in the same
    space) ends with exactly one favourite wallet, never zero and never two.
23. Every form body on the add/edit/archive/favourite actions is read within a size cap and answers 400 or 415,
    never 500, on a malformed or oversized body (reuse FN-01's `src/lib/server/forms.ts` guard, not a new one).
24. `{#each}` lists in the wallet group key by `wallet.id`, never by name or type.
25. Every Indonesian phrase added for this feature (wallet type labels "Tunai"/"Bank"/"E-wallet"/"Kartu
    kredit"/"Lainnya", form labels, empty/error/success copy) has an English entry in `i18n-en.ts`; the coverage
    test fails the build if one is missing.
26. Currency display anywhere on `/kekayaan` uses `formatMoney`/`formatMoneyCompact` from
    `src/lib/shared/money-format.ts`; no hand-built `Rp` string.
27. Focus returns to the opener when the add/edit `Sheet` closes; touch targets ≥ 44 px; WCAG AA contrast in both
    themes (reuses FN-00's token system, no new colours beyond the existing type-chip palette).
28. User-facing error text on this feature never contains a file path, stack trace, row id or internal
    identifier.
29. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression test
    (favourite-swap race, stale-`updated_at` edit, cross-space probe, last-4 validation) is shown failing on the
    unfixed code first (checklist › Tests › "Fail-before proof").

## Architecture notes

**Modules touched / added**

- `src/lib/server/db/schema.ts` — add one table (Drizzle), migration generated into `migrations/0002_wallets.sql`
  (renumber to `0003` at merge if FN-03's migration lands first):
  - `wallets (id pk text, space_id text not null references spaces.id, name text not null, type
    text not null check(type in ('tunai','bank','e_wallet','kartu_kredit','lainnya')), currency text not null
    default 'IDR', opening_balance_minor integer not null default 0, is_favourite integer not null default 0,
    last_four text, created_at integer not null, updated_at integer not null, deleted_at integer, seq integer not
    null)` — follows `CLAUDE.md` › Data and runtime conventions: every user-data table carries `space_id`,
    `updated_at`, `deleted_at` (tombstone) and a sync sequence. Index `(space_id, deleted_at)` for the list query;
    a partial-intent unique constraint on "one favourite per space" is **not** enforced in SQL (SQLite partial
    unique indexes exist but D1's guard pattern for this is the application-level guarded `db.batch` in
    criterion 11, matching checklist › Data access › "Concurrent writes" — a read-then-write inside one batch,
    not a second migration).
  - `seq` assignment (server-first, no client ever supplies it, per CLAUDE.md "never trust `seq` from the
    client"): a per-space monotonic counter. Simplest server-first option for this pass — reuse `spaces.updated_at`-
    style bookkeeping is overkill; instead maintain a small `app_meta`-style row keyed `seq:<space_id>` (reusing
    the existing `app_meta` table at `src/lib/server/db/schema.ts:4-8`, which already has exactly this
    key/value/updated_at shape) and increment it inside the same `db.batch` as the wallet write using an `UPDATE
    … RETURNING` guarded statement (checklist › Data access › "Concurrent writes"). FN-03's PRD or the sync
    design (`docs/ARCHITECTURE.md`) may define a shared `nextSeq(db, spaceId)` helper before FN-04 lands; if so,
    FN-04 must call that helper instead of inventing its own counter — check for it at implementation time and
    only fall back to the `app_meta` approach above if no shared helper exists yet.
- `src/lib/server/wallets/repo.ts`, `balance.ts`, `validation.ts` — new, as described in Scope.
- `src/lib/server/space-access.ts` (or wherever FN-03 lands it — **not yet written**; FN-03's PRD does not exist
  in this repo as of 2026-10-07) — FN-04 depends on it for every load/action. Expected contract, stated here so
  FN-04 can be implemented against it once FN-03 ships: given `locals.user` and a `spaceId` (resolved from the
  session's current space, never from a route param the client controls, unless FN-03 defines route params as
  the normal multi-space navigation — follow whatever FN-03's PRD specifies when it exists), return either `{
  spaceId, role }` (membership found) or a uniform not-found result — identical for "space does not exist" and
  "user is not a member" (no existence oracle, matching FN-01's own "one access rule" pattern at
  `docs/features/fn-01-accounts/PRD.md:93-94,139`). If FN-03 has not merged when FN-04 implementation starts,
  FN-04 is **blocked** on it per `docs/TASKS.md` phase ordering (FN-03 is Phase 0, FN-04 is Phase 1) — do not
  stub a local "pretend" helper; wait for FN-03's real one so there is exactly one access rule in the codebase
  (checklist › Access and privacy › "One access rule").
- `src/routes/(app)/kekayaan/+page.server.ts`, `+page.svelte` — as described in Scope; replaces the stub at
  `src/routes/(app)/kekayaan/+page.svelte:1-12`.
- `src/lib/shared/amount-input.ts` (`amountDigits`, `digitsToMinor` — FN-00 Task 10, expected to exist by FN-04
  implementation time) and `src/lib/ui/kit/AmountInput.svelte` — reused unchanged for the opening-balance field;
  FN-04 does not add money-parsing logic of its own.
- `src/lib/shared/money-format.ts` (`formatMoney`, `formatMoneyCompact`, `src/lib/shared/money-format.ts:36,62`) —
  reused unchanged for every balance figure.
- `src/lib/shared/i18n.ts` (`tr`/`trf`, `src/lib/shared/i18n.ts:20-28`) and `src/lib/shared/i18n-en.ts` — add every
  new phrase here.
- `src/lib/ui/shell/nav.ts` — no change needed; `/kekayaan` is already a tab (`src/lib/ui/shell/nav.ts:21`).
- `src/lib/server/db/index.ts` (`getDb`, `src/lib/server/db/index.ts:4`) — reused unchanged.
- `test/helpers/d1.ts` (`withLocalD1`) — reused unchanged for Vitest coverage of `repo.ts`/`balance.ts` against a

- Worker: app Worker only (SSR, loaders, actions) — no `workers/jobs` or `workers/inbound` involvement in FN-04.

## Owner decisions

**Answered by the owner 2026-10-08: accept every proposed default below as written.**


- **C. Where the wallets UI lives.** *Proposed default (adopted above):* Kekayaan tab (`/kekayaan`) only, no
  `/pengaturan/dompet`. Trade-off: once FN-25 (net worth) and FN-26/27/28 (subscriptions, belongings,
  collectibles) also land on `/kekayaan`, the screen will need its own sub-navigation (today it is just the
  wallet group); that restructuring is deferred to whichever of those features lands next, not solved now. The
  alternative (a dedicated `/pengaturan/dompet` settings screen now) would cost extra route/i18n work this pass
  for no additional capability, since Kekayaan already has the empty stub to fill.
- **D. Opening balance sign for a credit-card wallet.** The "Mirror" note treats "Kartu kredit" as its own
  wallet type with no stated sign convention. *Proposed default:* allow a negative `openingBalanceMinor` for any
  wallet type (a credit card carrying a balance is naturally negative; a cash/bank wallet is normally
  non-negative but not blocked from going negative, since FN-05 transactions can overdraw it later). Trade-off:
  the UI must not assume balance ≥ 0 anywhere (e.g. compact formatting, colour) — `formatMoney`/
  `formatMoneyCompact` already handle negative minor units correctly (`src/lib/shared/money-format.ts:49,66`), so
  this costs nothing extra, but it is an explicit choice to flag rather than silently allow.
- **E. "Investasi" as a type.** `docs/FEATURES.md` FN-04 lists "Investasi as a category group" alongside the
  wallet types. *Proposed default:* do not add `investasi` to the `wallets.type` enum this pass — it belongs to
  FN-25 Net worth's asset classes (Kas, Investasi, Kripto, Emas, Properti & aset), not to a transactional wallet.
  Trade-off: if FN-25 instead expects investment holdings to be modeled as a wallet subtype, the enum gets a
  migration then; flagging now so FN-25's PRD author checks this choice before assuming either shape.
