# FN-01 Account and sign-in — PRD

Catalog entry: `docs/FEATURES.md` › FN-01. Phase: 0 — Foundation. Tracker: `docs/TASKS.md` › Phase 0 ›
"FN-01 Account and sign-in. Risk: Large." Risk tier: **Large** (new auth subsystem, new tables, touches every
`(app)` route through `hooks.server.ts`).

Owner decisions already fixed for this pass (2026-10-07, do not re-litigate): e-mail + password only (no Google
sign-in yet); storage is server-first in D1 (no guest/local-first in this feature); auth approach ported from
The earlier project (`~/projects/earlier-project`); scope is sign up, sign in, sign out, session middleware, `/pengaturan/akun`
(sign-out + delete account); password reset by e-mail is deferred (no e-mail provider yet); the account key
(FN-21) is out of scope; FN-01 creates the personal `spaces` row + owner `space_members` row at sign-up so FN-03
extends the same tables.

## Goal

Every later feature (wallets, transactions, budgets, the assistant) is either guest-only or needs a durable,
isolated owner for its rows. FN-01 is the one gate the whole app walks through: a person can create an account in
seconds, come back and be recognised, leave a device without leaving a live session behind, and delete everything
MONTRA holds about them from Settings. Without it, nothing server-first (D1-backed) in Phases 0–1 has anywhere
to attach its rows, and the main journey ("open app → add a wallet → … → sign up → connect Gmail → …") has no
step 5.

## Scope

- **Migration `0001`** (`migrations/0001_*.sql`, generated by `drizzle-kit generate` from
  `src/lib/server/db/schema.ts`, applied only through `npm run db:migrate:local`): tables `users`,
  `user_passwords`, `sessions`, `auth_attempts`, `spaces`, `space_members` (see Architecture notes for columns).
- **`src/lib/server/auth/`** (new): `password.ts` (PBKDF2 derive, strength check, `signInWithPassword`,

  counter), `accounts.ts` (sign-up: create `users` + `user_passwords` + personal `spaces` + owner
  `space_members` row in one `db.batch`), `delete-account.ts` (delete a user's own rows).
- **`src/hooks.server.ts`**: extend with `locals.db`, `locals.user`, `locals.sessionToken`; resolve the session
  cookie on every request; redirect unauthenticated requests to `(app)` routes to `/masuk?next=…`; leave `/masuk`,
  `/daftar`, the `(site)` tree, `/api/v1/health` and static assets public.
- **Routes:**
  - `src/routes/(app)/daftar/+page.svelte` + `+page.server.ts` — sign-up form (name, e-mail, password, 18+
    confirmation checkbox) and its form action. Note: FN-00's stub list puts `/daftar` under the public stub set;
    FN-01 turns it into a real, unauthenticated-only page (redirects signed-in users to `/`).
  - `src/routes/(app)/masuk/+page.svelte` + `+page.server.ts` — sign-in form and action.
  - `src/routes/(app)/pengaturan/akun/+page.svelte` + `+page.server.ts` — shows name/e-mail/created-at (WIB);
    actions `signOut` (revoke the current session only) and `deleteAccount` (re-enter password, then delete).
  - `src/routes/(site)/site/hapus-akun/+page.svelte` — filled in per Owner decision B below.
- **i18n:** every new Indonesian phrase in this feature added to `src/lib/shared/i18n.ts` call sites, with an
  English entry in `src/lib/shared/i18n-en.ts` (coverage test already gates this, `src/lib/shared/i18n.test.ts`).
- **UI states:** loading (submitting), empty (n/a — forms), error (inline per-field + banner), saving (button
  spinner/disabled on submit), success (redirect only after the write is confirmed by the server, per
  `CLAUDE.md` › UI and routes).

- Shared spaces, invites, roles beyond "owner", several spaces per user (FN-03 extends `spaces`/`space_members`).
- Password reset by e-mail, e-mail verification of the sign-up address (no e-mail provider configured — see
  Prerequisites).
- The account key / sealed uploads (FN-21).
- TOTP/2FA, passkeys, audit-log table (not required by any FN-01 acceptance row; revisit with FN-31 if the owner
  wants a sign-in audit trail).
- Any guardian-consent verification flow for under-18 users (self-attestation only — see Owner decision D).
- Rate-limit dashboards, admin tooling, account suspension.

## Acceptance criteria

**Sign-up (`/daftar`)**

1. Given a signed-out visitor at `/daftar`, when they submit name, e-mail, a password, and tick the 18+/guardian
   confirmation, then a `users` row, a `user_passwords` row, a `spaces` row (`kind = 'personal'`) and a
   `space_members` row (`role = 'owner'`) are created in one `db.batch`, a session is created and its cookie set,
   and the response redirects to `/` signed in.
2. Given the same request without the 18+ checkbox ticked, when submitted, then the action fails with a field
   error (`tr()`/English via `i18n-en.ts`) and no row is written.
3. Given a password shorter than the configured minimum (Owner decision C) or on the common-password list, when
   submitted, then the action fails with the specific reason and no row is written.
4. Given an e-mail already registered, when submitted, then the action fails with "E-mail sudah terdaftar" (and
   English) — unlike `/masuk`, this message is allowed to say the account exists, matching common sign-up UX.
5. Given 20+ concurrent sign-up submissions with the same e-mail (pre-handoff concurrency probe), when they race,
   then the `users.email` unique index lets exactly one succeed and the rest fail with the duplicate-e-mail
   message, never a 500.
6. Given the name field contains control or zero-width characters, when submitted, then they are stripped and the
   length capped before storage (checklist › Access and privacy › Untrusted text).
7. Given JavaScript is disabled, when the sign-up form is submitted, then it still works as a normal form POST
   (progressive enhancement; checklist › Tests › pre-handoff "No-JS forms").
8. Given a signed-in user navigates to `/daftar`, when the page loads, then they are redirected to `/` (no
   re-sign-up while signed in).

**Sign-in (`/masuk`)**

9. Given correct e-mail and password, when submitted, then a new session is created, its cookie set with
   `HttpOnly`, `SameSite=Lax`, `Secure` in a secure deployment (and `__Host-`-prefixed name, matching
   `secureDeployment()`/`sessionCookieName()` pattern), and the response redirects to `next` (default `/`).
10. Given a wrong password, an unknown e-mail, or a locked account, when submitted, then the response is the same
    generic "E-mail atau kata sandi salah" message in every case (no account-existence oracle — same status,
    body shape and comparable timing), per checklist › Access and privacy › "One access rule" / no existence
    oracle.
11. Given 5 wrong passwords in a row for one account (within the lockout window), when a 6th attempt (even the
    correct password) is submitted, then it is refused until the lockout expires, and the account's `failed_count`
    / `locked_until` are updated in the same guarded statement that checks them (no read-then-write race; checklist
    › Data access › "Concurrent writes").
12. Given more than the configured attempts from one client in the throttle window (reusing the earlier project's per-client
    throttle shape), when further sign-in attempts arrive, then they are refused before any password is derived.
13. Given a reload after signing in, when the browser requests any `(app)` page, then the session cookie keeps the
    user signed in (persisted state survives reload).
14. Given JavaScript is disabled, when the sign-in form is submitted, then it still works as a normal form POST.

**Session middleware / route protection**

15. Given a request to any `(app)` route with no live session, when it is a `GET`, then `hooks.server.ts` redirects
    to `/masuk?next=<original path>`; when it is not a `GET` (a form action/API write), then it answers 401, never
    a silent pass-through.
16. Given a request to `/masuk`, `/daftar`, any `(site)` route, or `/api/v1/health`, when there is no session, then
    the request is served normally (no redirect loop).
17. Given a session whose `expires_at` has passed or whose `revoked_at` is set, when a request carries its cookie,
    then it is treated as signed out and the cookie is cleared.
18. Given two devices signed in as the same user (pre-handoff "two devices" probe), when one device signs out,
    then only that device's session is revoked; the other device's session stays live.

**Account page (`/pengaturan/akun`)**

19. Given a signed-in user, when `/pengaturan/akun` loads, then it shows name, e-mail and "Akun dibuat pada" in
    WIB (converted from the UTC `created_at`), with a loading skeleton while the load runs and an error state with
    retry if the load fails.
20. Given the "Keluar" (sign out) action, when submitted, then the current session's `revoked_at` is set, its
    cookie cleared, and the response redirects to `/masuk`; a success state is never shown before the server
    confirms the revocation.
21. Given the "Hapus akun" (delete account) action, when the user re-enters their current password and confirms,
    then (in one batch) the user's `sessions`, `user_passwords`, `space_members` and (for a personal space with no
    other member) `spaces` rows are deleted, the `users` row is deleted, and the response signs the browser out and
    redirects to a public confirmation page; a wrong password re-entry leaves every row untouched and shows the
    same inline error as a wrong sign-in.
22. Given the delete succeeds, when the (deferred) public `/hapus-akun` page is later wired to real deletion
    (Owner decision B), then it must reuse this same delete path — never a second, divergent implementation.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

23. Every new load function and form action that reads or writes a `users`/`sessions`/`user_passwords`/
    `spaces`/`space_members` row operates only on `event.locals.user.id` (or the session token), never a client-
    supplied user id — there is no "space-access helper" bypass to check here because FN-01's tables are
    account-level, not space-scoped financial data (the helper itself is FN-03's deliverable).
24. Every redirect target (`next=`) is validated with a shared safe-return helper (ported from the earlier project's
    `safeReturnTo`, `earlier-project/src/lib/server/util.ts:230`), never a bare `startsWith('/')` check.
25. Every form body on `/daftar`, `/masuk`, and the account-page actions is read within a size cap and answers 400
    or 415, never 500, on a malformed or oversized body (pattern: `earlier-project/src/lib/server/forms.ts`).
26. `{#each}` lists (none expected in FN-01 UI beyond a single account card) key by id if any list is added later.
27. Every Indonesian phrase added for this feature has an English entry in `i18n-en.ts`; `npm run test` (the
    coverage test) fails if one is missing.
28. Focus returns correctly after any sheet/dialog used on these pages; touch targets ≥ 44 px; WCAG AA contrast in
    both themes (reuses the FN-00 token system, no new colours).
29. User-facing error text never contains a file path, stack trace, or internal identifier (session id, row id).
30. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression test
    is shown failing on the unfixed code first (checklist › Tests › "Fail-before proof").

## Prerequisites

- No new external credentials needed to ship sign-up/sign-in/sign-out/in-app delete: PBKDF2 and sessions use only
  WebCrypto and D1, already available locally and in any deployed Worker.
- **Password reset by e-mail** needs an e-mail-sending provider. No secret name exists yet in
  `.dev.vars.example` (currently only lists `DEV_ROUTES`); when the owner picks a provider (e.g. Resend/Postmark/
  SES), add its secret there and gate the "Lupa kata sandi" link: while unset, the link is hidden or shows
  "Belum dikonfigurasi" rather than a dead form. **Deferred in this pass** — no reset flow ships now.
- **Public `/hapus-akun` without signing in** needs the same e-mail provider if it is to process a request
  asynchronously (Owner decision B); until then it degrades to the behaviour decided there.
- Cloudflare Workers Paid plan (already an owner prerequisite from `docs/TASKS.md`) matters here specifically

  `earlier-project/src/lib/server/auth/password.ts:14-20`); this is already tracked as an owner prerequisite,
  not a new one.

## Owner decisions

**Answered by the owner 2026-10-07 — these override the proposed defaults below:** A = 30-day absolute session, no
idle logout (default kept). B and E = defer both: `/hapus-akun` explanation page + `mailto:` request link; no
e-mail verification (default kept). **C = minimum password length 8 characters (not 12).** D = self-attested
18+/guardian checkbox (default kept). Every acceptance criterion or constant that says 12 characters means 8.

Proposed defaults as originally written:

- **A. Session lifetime & idle timeout.** The earlier project (enterprise intel tool) uses a 12-hour absolute session plus a
  60-minute idle revocation. MONTRA is a personal-finance PWA people expect to stay signed into for weeks.
  *Proposed default:* 30-day absolute `SESSION_TTL_MS`, no separate idle timeout (a "remember me" consumer app
  posture), with `last_seen_at` still touched for later analytics use, not for revocation. Trade-off: weaker
  against a stolen unlocked device than the earlier project's posture, acceptable for a non-custodial app that moves no money.
- **B. Public `/hapus-akun` (delete without the app).** A fully self-serve public delete needs the deferred
  e-mail provider to confirm the request came from the account owner. *Proposed default:* ship `/hapus-akun` now
  as an explanation page plus a `mailto:` link to a support address, with a visible note that the fastest path is
  signing in and using Pengaturan › Akun; wire it to a real, provider-verified self-serve flow once the e-mail
  provider is chosen. Trade-off: not literally "usable without the app" end-to-end yet, only as a request path.
- **C. Password strength floor.** The earlier project requires a 12-character minimum (enterprise). *Proposed default:* keep
  12 characters minimum for MONTRA too (consistency with the ported code and constant, no separate rule to
  maintain), accepting some sign-up friction versus a shorter, more "consumer app"-typical minimum (e.g. 8).
- **D. Under-18 handling.** *Proposed default:* a single self-attested checkbox ("Saya berusia 18 tahun ke atas,
  atau sudah mendapat izin wali") with no guardian-identity verification in this pass — matches the feature
  catalog's own wording ("18+ (younger with guardian permission)") without building a guardian-consent flow this
  pass. Trade-off: unenforceable without identity verification, same posture most consumer apps take.
- **E. E-mail verification at sign-up.** *Proposed default:* none in this pass (account usable immediately after
  sign-up) — verification needs the same deferred e-mail provider as password reset; ship both together later.
  Trade-off: a mistyped or borrowed e-mail address can create an account that never confirms ownership until
  password reset exists.
