# FN-12 Feature toggles — PRD

Catalog entry: `docs/FEATURES.md` › FN-12 (line 105-108). Phase: 1 — Core ledger. Tracker: `docs/TASKS.md` ›
Phase 1 › "... FN-11 Drafts inbox · **FN-12 Feature toggles** · FN-13 PWA and push" (`docs/TASKS.md:61-62`). Risk
tier: **Small** (one small, non-financial table with no `space_id`; one new settings page; a small filter change
to the two nav components every page renders — the only reason this is not trivially tiny is that `Sidebar`/
`TabBar` are shared chrome, so the change's blast radius is "every page" even though the logic itself is a few
lines).

Owner decisions already fixed before this pass (do not re-litigate): server-first in D1, signed-in only; depends
on FN-01's `locals.user` only — this feature touches no space-scoped financial data at all. Migration number is
**`0008`** (chain: FN-01 `0001` … FN-10 Goals `0006`, FN-11 Drafts `0007`, this feature `0008` — renumber at
merge if the actual landing order differs).

## Goal

`docs/FEATURES.md`'s own line is explicit that "all modules feed the same numbers" (line 108) — this is a nav
declutter preference, not a data-scoping feature. A user who never uses net worth, subscriptions, belongings or
collectibles should be able to hide those tabs from their own view without affecting what their household sees
or what any total adds up to. Today `/pengaturan` itself is still the generic `[stub=stub]` placeholder
(`src/routes/(app)/[stub=stub]/+page.svelte`) with no real page behind the "Pengaturan" sidebar link
(`src/lib/ui/shell/nav.ts:27`) at all, and `Sidebar`/`TabBar` render their nav arrays unconditionally
(`src/lib/ui/shell/Sidebar.svelte:15`, `src/lib/ui/shell/TabBar.svelte:12`) — this feature both ships the toggle
screen FEATURES.md asks for and, as the minimum needed to make it reachable, the first real `/pengaturan` index
page.

## Scope

- **Migration `0008`** (`migrations/0008_feature_flags.sql`, generated by `drizzle-kit generate` from an added
  `feature_flags` table in `src/lib/server/db/schema.ts`): one table, `feature_flags` (columns under Architecture
  notes) — **per user, not per space** (Owner decision A).
- **`src/lib/server/feature-flags/`** (new): `repo.ts` (`getFeatureFlags(db, userId)` → `Record<Module, boolean>`
  for all 5 modules, defaulting a module with no row to `true` — toggles are default-on, matching "turns modules
  on or off" rather than an opt-in list; `setFeatureFlag(db, userId, module, enabled)` — one guarded upsert:
  `INSERT … ON CONFLICT(user_id, module) DO UPDATE SET enabled = ?, updated_at = ?`), `modules.ts` (the fixed
  5-value `Module` union and its i18n labels, one file so no later feature re-declares the list).
- **New UI kit primitive:** `src/lib/ui/kit/Toggle.svelte` — an accessible on/off switch (`role="switch"`,
  `aria-checked`, `bindable checked`, `label`, `disabled`), 44 px touch target, degrading to a plain `<input
  type="checkbox">` semantics so the enclosing `<form>` still submits a value with JavaScript off. No other kit
  component today provides this shape (`Chip`'s `aria-pressed` toggles a selection state, not a persisted
  on/off setting) — this is the one new primitive this feature adds, named here so FN-13's own device-notification
  toggle reuses it rather than building a second switch (see FN-13's PRD, Architecture notes).
- **Routes** (all under `(app)`, session-gated; no space resolution needed — this feature never reads
  `locals.space`):
  - `src/routes/(app)/pengaturan/+page.server.ts` + `+page.svelte` (new — replaces the `[stub=stub]` rendering
    for exactly the `pengaturan` slug, same pattern FN-03 used for `ruang`) — a plain `GroupList` of links to
    every settings sub-page that exists by the time this feature ships (at minimum `/pengaturan/akun`,
    `/pengaturan/kategori`, and this feature's own `/pengaturan/fitur`); a feature that ships a settings
    sub-page later adds its own row to this same index rather than building a second index page (stated here as
    a cross-feature contract, the same way FN-05/FN-07 named `src/lib/shared/dates.ts` as "whichever lands first
    builds it, the other imports it").
  - `src/routes/(app)/pengaturan/fitur/+page.server.ts` + `+page.svelte` (new) — `load` calls
    `getFeatureFlags(db, locals.user.id)`; renders one `GroupRow` + `Toggle` per module (Kekayaan, Langganan,
    Barang, Koleksi, Ruang bersama); a module with no nav entry to hide yet (see criterion 7) shows a small
    caption "Belum ada menu untuk disembunyikan" under its row so the toggle's current lack of visible effect is
    explained, not silently absent; action `setFlag` (one `<form>` per row, submits on toggle, works without JS
    as a checkbox + implicit submit via a per-row submit button).
- **Touched:** `src/lib/ui/shell/Sidebar.svelte` and `src/lib/ui/shell/TabBar.svelte` — both currently render
  their nav arrays unconditionally; each gains a `hiddenModules: ReadonlySet<Module>` prop (sourced from a new
  `src/routes/(app)/+layout.server.ts` load calling `getFeatureFlags`, passed down through
  `src/routes/(app)/+layout.svelte`) and filters out the `TABS` entry whose `href` maps to a hidden module before
  rendering. `TabBar.svelte`'s `.tabbar` CSS grid (`grid-template-columns: repeat(5, 1fr)`, hardcoded for exactly
  4 tabs + 1 add button, `src/lib/ui/shell/TabBar.svelte:36`) becomes `repeat(${visibleTabs.length + 1}, 1fr)` so
  hiding a tab never leaves an empty grid column.
- **`src/params/stub.ts`** — remove `'pengaturan'` from the stub `SLUGS` set.
- **i18n:** module labels ("Kekayaan" already exists; add "Langganan", "Barang", "Koleksi", "Ruang bersama" as
  settings-row labels — these are plain nouns, not the eventual tab labels those future features will define
  themselves), "Belum ada menu untuk disembunyikan", "Fitur", "Pengaturan" (if not already present) — added to
  `src/lib/shared/i18n.ts` call sites with English entries in `i18n-en.ts`; coverage test fails the build if one
  is missing.
- **UI states:** loading (skeleton rows on `/pengaturan` and `/pengaturan/fitur` while `load` runs), empty (n/a —
  the module list is fixed and always has 5 rows), error (`ErrorState` with retry on a failed load), saving
  (toggle disabled mid-submit), success (the toggle's new state is shown only after the server confirms the
  write, and the shell's own `Sidebar`/`TabBar` update on the next layout re-render SvelteKit already performs
  after a same-route form action — no separate client-side state to keep in sync by hand).

## Out of scope

- Per-space toggles, or any toggle that affects what a shared-space member other than the signed-in user sees
  (Owner decision A — per user only).
- Any new nav entry for Langganan, Barang, Koleksi or Ruang bersama. `Ruang` (`/ruang`) has no `Sidebar`/`TabBar`
  entry today (it is reached only by direct navigation or FN-03's own screens, per
  `docs/features/fn-03-spaces/PRD.md:68`); Langganan/Barang/Koleksi do not exist yet (FN-26/27/28, Phase 4).
  Toggling any of those four persists correctly (criterion 2) but has no visible nav effect this pass — this is
  stated plainly in the UI (the caption above), not hidden from the owner as a silent gap.
- Blocking or redirecting direct navigation to a hidden module's route. Hiding Kekayaan removes its nav entry
  only; `/kekayaan` itself still loads normally if visited directly (Owner decision D).
- Sub-section toggles within Kekayaan (e.g. hiding just the net-worth chart while keeping wallets visible) — the
  mirror's "Kekayaan" is one module, one toggle; sub-section toggles are a later extension of the same `module`
  enum, not built now.
- Guest/signed-out access to `/pengaturan/fitur` — this feature requires `locals.user` like every other settings
  page; a signed-out visitor is redirected to sign in by the existing session gate, not given a local-only
  preference.
- Sync (IndexedDB) of `feature_flags` — out of scope per the storage decision; this table has no `seq`/
  `deleted_at` at all (see Architecture notes), so there is nothing for a future sync layer to pull without a
  schema change.

## Acceptance criteria

1. Given a signed-in user with no `feature_flags` rows yet, when `/pengaturan/fitur` loads, then all 5 modules
   (Kekayaan, Langganan, Barang, Koleksi, Ruang bersama) show as enabled (default-on) — no row defaults to
   hidden.
2. Given the "Kekayaan" toggle is switched off and submitted, then one `feature_flags` row is written
   (`user_id = locals.user.id`, `module = 'kekayaan'`, `enabled = 0`) scoped only to that user — never to a
   `space_id`, never visible to or affecting any other member of a shared space.
3. Given the same toggle, when the page is reloaded (full refresh), then it is still off — persisted state
   survives reload.
4. Given "Kekayaan" is off, when any `(app)` page loads afterward, then the bottom `TabBar` and the desktop
   `Sidebar` both omit the Kekayaan entry, and `TabBar`'s grid column count matches the remaining visible tab
   count plus the Add button exactly — no empty gap, no overlapping columns.
5. Given "Kekayaan" is switched back on, then it reappears in its original fixed position in both `TabBar` and
   `Sidebar` (tab order is a static constant, never reordered by toggle history).
6. Given "Kekayaan" is off, when `/kekayaan` is requested directly by URL, then it still loads and renders
   normally — the toggle hides a nav entry, it never blocks a route or changes what data that route shows
   (Owner decision D; "all modules feed the same numbers" is unaffected, `docs/FEATURES.md:108`).
7. Given the "Langganan", "Barang", "Koleksi" or "Ruang bersama" toggle is switched off, then its row's state
   persists and survives reload exactly like criterion 2–3, and its row shows "Belum ada menu untuk
   disembunyikan" (and English) — these four have no current nav entry to remove, and the UI says so rather than
   implying an effect that does not exist yet.
8. Given 20 concurrent submissions toggling the same module for the same user (pre-handoff concurrency probe),
   when they race, then the `(user_id, module)` unique index guarantees exactly one row for that pair afterward
   (never two rows, never a unique-constraint 500) and its final `enabled` value is whichever write was last
   applied — a single boolean preference has no "exactly one winner must hold a limited slot" invariant to
   prove, unlike FN-04's favourite-wallet or FN-03's 5-member cap.
9. Given JavaScript is disabled, when a toggle row's form is submitted, then it still works as a normal form
   POST (the `Toggle` component's checkbox semantics degrade to a plain checkbox + submit button).
10. Given a signed-out visitor, when `/pengaturan/fitur` or `/pengaturan` is requested, then the existing
    session gate redirects them to sign in — no local-only, account-free preference exists this pass.
11. Given `/pengaturan` loads, then it lists a link to every settings sub-page that exists at build time (at
    least Akun, Kategori, Fitur) with a loading skeleton while the load runs and a retry state on failure; this
    replaces the generic "Segera hadir" stub for exactly the `pengaturan` slug (`src/params/stub.ts:1` loses
    that entry).
12. This feature shows no money figure and no transaction date anywhere — the task's money/WIB-bucketing
    requirement is explicitly vacuous here; stated so the qa-tester does not look for a check that cannot exist
    on this screen.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

13. Every load and action under `/pengaturan`, `/pengaturan/fitur` resolves the acting user from
    `event.locals.user` — never a client-supplied user id; no cross-user probe is meaningful here since no id
    is ever read from a route param or form field (the user can only toggle their own flags).
14. Every form body on the `setFlag` action is read within a size cap and answers 400 or 415, never 500, on a
    malformed or oversized body (reuse FN-01's `src/lib/server/forms.ts` guard, not a new one).
15. `{#each}` lists (the 5 module rows, the settings index links) key by `module`/route id, never by label text.
16. Every Indonesian phrase added for this feature has an English entry in `i18n-en.ts`; the coverage test
    fails the build if one is missing.
17. Touch targets ≥ 44 px (the new `Toggle` primitive); WCAG AA contrast in both themes (FN-00 token system, no
    new colours); focus behaves correctly on toggle (no sheet to return focus to, since this is an inline
    switch, not a dialog).
18. User-facing error text on this feature never contains a file path, stack trace, row id or internal
    identifier.
19. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression
    test (concurrent-toggle race, TabBar grid-column count after hiding a tab, direct-URL access to a hidden
    module) is shown failing on the unfixed code first (checklist › Tests › "Fail-before proof").

## Architecture notes

**Modules touched / added**

- `src/lib/server/db/schema.ts` — add one table (Drizzle), migration generated into
  `migrations/0008_feature_flags.sql`:
  - `feature_flags (id pk text, user_id text not null references users.id, module text not null check(module in
    ('kekayaan','langganan','barang','koleksi','ruang')), enabled integer not null default 1, created_at integer
    not null, updated_at integer not null)`. Unique index `(user_id, module)`. **No `space_id`, `deleted_at` or
    `seq`** — this is a per-user display preference, not space-scoped financial data; FN-01's own `sessions` and
    `user_passwords` tables are the existing precedent for a user-level table with no `space_id`
    (`docs/features/fn-01-accounts/PRD.md:162-168`). A row is overwritten in place (upsert), never tombstoned,
    since there is no sync layer reading this table and no history to preserve — if a later pass adds
    cross-device sync of preferences, that is a new column, not a retrofit of this one.
- `src/lib/server/feature-flags/` — new, as described in Scope.
- `src/lib/ui/kit/Toggle.svelte` — new primitive, as described in Scope. FN-13's own "Beri tahu di perangkat
  ini" switch must reuse this component rather than building a second one — whichever of FN-12/FN-13 lands first
  builds it, the other imports it (same "whichever lands first" rule FN-05/FN-07 used for
  `src/lib/shared/dates.ts`); per `docs/TASKS.md`'s stated Phase 1 order (FN-11 → FN-12 → FN-13) FN-12 is
  expected to land first, so this PRD treats `Toggle.svelte` as built here.
- `src/routes/(app)/pengaturan/`, `/pengaturan/fitur/` — new trees; `src/params/stub.ts` loses `'pengaturan'`
  from `SLUGS`.
- `src/routes/(app)/+layout.server.ts` (**new** — no load exists on this layout today, only the route-group
  wraps `+layout.svelte`) — calls `getFeatureFlags(db, locals.user.id)` and returns `{ hiddenModules }` (the set
  of modules with `enabled = false`) for `+layout.svelte` to pass to `Sidebar`/`TabBar`.
- `src/lib/ui/shell/Sidebar.svelte`, `src/lib/ui/shell/TabBar.svelte` — both touched as described in Scope; the
  module-to-`href` mapping (`kekayaan` → `/kekayaan`) lives in `src/lib/ui/shell/nav.ts` as a small lookup table
  next to `TABS`, not duplicated in each component.
- `src/routes/(app)/+layout.svelte` — touched to read the new layout-server data and pass `hiddenModules` down
  to `Sidebar`/`TabBar`.
- `src/lib/shared/i18n.ts`/`i18n-en.ts` — add every new phrase.
- Worker: app Worker only (SSR, loaders, actions) — no `workers/jobs`/`workers/inbound` involvement.

**Reuse / do not duplicate**

- One switch primitive (`Toggle.svelte`) for every on/off preference in the app, starting here and reused by
  FN-13 — do not let FN-13 build a second one.
- One settings index page (`/pengaturan`) — every later settings-owning feature adds a row to it, never a
  second index.
- Do not add a second form-body guard; reuse FN-01's.

## Owner decisions

**Every decision below is auto-accepted per owner instruction 2026-10-08 ("just auto accept your recomm"). No
open questions remain.**

- **A. Per space or per user.** *Proposed default (auto-accepted per owner instruction 2026-10-08):* per user —
  `feature_flags.user_id`, no `space_id` at all. *Trade-off:* in a shared space, one member hiding Kekayaan from
  their own view has no effect on what their partner sees; the alternative (per space, binding to every member)
  would force a household to agree on one shared nav layout for a purely cosmetic preference, which does not
  match "all modules feed the same numbers" (a display choice, not a data-access choice).
- **B. Default state of a toggle with no row.** *Proposed default (auto-accepted per owner instruction
  2026-10-08):* enabled (default-on) — matches the mirror's framing ("turns modules on or off", not "modules are
  off until enabled", `docs/FEATURES.md:107`). *Trade-off:* none significant; a brand-new user sees every module
  they are entitled to by default.
- **C. Toggling a not-yet-built module's nav entry.** *Proposed default (auto-accepted per owner instruction
  2026-10-08):* ship all 5 toggle rows now, with an explicit "Belum ada menu untuk disembunyikan" caption on the
  four with no current nav effect (criterion 7), rather than hiding those rows until their modules exist.
  *Trade-off:* a user may toggle Langganan off today expecting an effect that does not yet exist; the caption is
  the mitigation. The alternative — showing only "Kekayaan" until the others are built — would mean adding a
  settings-row migration for every later module instead of reserving all 5 values now.
- **D. Hiding a nav entry vs. blocking the route.** *Proposed default (auto-accepted per owner instruction
  2026-10-08):* nav-entry hiding only; the underlying route is never blocked or redirected (criterion 6).
  *Trade-off:* a user who hides Kekayaan can still reach `/kekayaan` via an old bookmark or browser history; the
  alternative (404 or redirect the route itself) would turn a declutter preference into an access-control
  feature, which this table's shape (no space-isolation concern, no financial gating) does not warrant.
