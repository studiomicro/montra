# FN-21 Account key and sealed results — PRD

Catalog entry: `docs/FEATURES.md` › FN-21 (line 222-234). Phase: 2 — Capture. Tracker: `docs/TASKS.md` › Phase 2 ›
"FN-21 Account key and sealed results (before FN-15/FN-16 store any result)" (`docs/TASKS.md:68`). Risk tier:
**Large** (a migration, a new cryptographic key-management subsystem touching sign-up/sign-in, and the exact
mechanism `CLAUDE.md`'s "money and data are never invented" trust model leans on for every future uploaded
result — per `/build-feature`'s own risk table).

Owner decisions already fixed before this pass (do not re-litigate): server-first in D1, signed-in only (an
account key has no meaning for a guest with no server account); depends on FN-01 (`users`, sessions,
`/pengaturan/akun`) — FN-01 ships no password-change action, so this feature adds one (see Scope; FN-01's own
out-of-scope list confirms this, `docs/features/fn-01-accounts/PRD.md:56`: "Password reset by e-mail... The
account key / sealed uploads (FN-21)" are both named as explicitly not FN-01's job). Migration number is
**`0011`** (chain: FN-01 `0001` … FN-13 PWA `0009`, FN-18 CSV `0010`, this feature `0011` — renumber at merge if
the actual landing order differs).

## Goal

`docs/ARCHITECTURE.md` already locks the shape: "uploaded statements, screenshots and receipt photos are
processed in memory only and never stored... results sealed to the account key" (`docs/FEATURES.md:224-226`), and
every later AI-read feature (FN-15 receipt, FN-16 statement, FN-25 portfolio screenshots) depends on that key
existing *before* it reads its first file — `docs/TASKS.md` states this ordering explicitly: "FN-21... before
FN-15/FN-16 store any result" (`docs/TASKS.md:68`). Without FN-21, there is no way to honour the trust promise
`docs/PRD.md` makes under "Trust": "uploads never stored and results sealed to the account key" (`docs/PRD.md:66`)
— and once an AI-read feature ships without it, retrofitting sealing onto results already sitting in D1/R2 in the
clear is a much harder problem than building the key first. FN-21 ships exactly the key-management plumbing
(generate, wrap, unwrap, re-wrap on password change, seal, unseal) with no real producer calling it yet — the
same "mechanism now, real caller later" precedent FN-11 already set for the `drafts` table
(`docs/features/fn-11-inbox/PRD.md:19-24`).

## Scope

- **Migration `0011`** (`migrations/0011_account_keys.sql`, generated by `drizzle-kit generate` from an added
  `account_keys` table in `src/lib/server/db/schema.ts`): one table, `account_keys` — one row per user (columns
  under Architecture notes), named in `docs/ARCHITECTURE.md`'s own data model already
  (`docs/ARCHITECTURE.md:71`: "`account_keys`").
- **`src/lib/shared/account-key.ts`** (new, pure WebCrypto + one vetted hashing library — no D1/Workers
  dependency, runs unchanged in the browser and (for the sealing half only) in the Worker, per `CLAUDE.md` ›
  "shared domain code... so the client and Worker run the same logic"):
  - `isAccountKeySupported(): Promise<boolean>` — feature-detects X25519 `deriveBits` support by attempting a
    throwaway `crypto.subtle.generateKey({ name: 'X25519' }, true, ['deriveBits'])` in a `try`/`catch` (never a
    user-agent string check) — see Architecture notes "Official references checked" for the browser/runtime
    versions this guards against.
  - `generateKeyPair(): Promise<{ publicKeyRaw: Uint8Array; privateKey: CryptoKey }>` — `crypto.subtle
    .generateKey('X25519', true, ['deriveBits'])`, public key exported raw (32 bytes).
  - `deriveWrapKey(password: string, salt: Uint8Array, params: ScryptParams): Promise<CryptoKey>` — scrypt via
    the vetted `@noble/hashes/scrypt` implementation (Cure53-audited 2022, zero runtime dependencies, works
    unchanged in browsers, Cloudflare Workers, Node and Bun — see Architecture notes), its raw output bytes
    imported into an AES-256-GCM `CryptoKey` via `crypto.subtle.importKey('raw', ...)` (WebCrypto itself has no
    native scrypt, hence the named library — `CLAUDE.md`'s own instruction: "if scrypt is not in WebCrypto, name
    a vetted library").
  - `wrapPrivateKey(privateKey: CryptoKey, wrapKey: CryptoKey): Promise<{ wrapped: Uint8Array; nonce: Uint8Array
    }>` — exports the private key raw, encrypts it with AES-256-GCM under a fresh random 12-byte nonce
    (`crypto.getRandomValues`).
  - `unwrapPrivateKey(wrapped: Uint8Array, nonce: Uint8Array, wrapKey: CryptoKey): Promise<CryptoKey | null>` —
    AES-256-GCM decrypt; a GCM authentication-tag mismatch (wrong password) throws inside `crypto.subtle.decrypt`
    and is caught, returning `null` — never a partial or garbage key.
  - `sealToPublicKey(plaintext: Uint8Array, recipientPublicKeyRaw: Uint8Array): Promise<SealedBlob>` — generates
    an ephemeral X25519 key pair, `deriveBits` against the recipient's public key, HKDF-SHA256 over the shared
    secret to derive a one-time AES-256-GCM key, a fresh random nonce, and encrypts; returns `{
    ephemeralPublicKey, nonce, ciphertext }` (self-describing — the recipient needs nothing else to unseal).
  - `unseal(sealed: SealedBlob, recipientPrivateKey: CryptoKey): Promise<Uint8Array>` — mirrors `sealToPublicKey`
    in reverse; throws on authentication failure, never returns corrupted plaintext.
- **`src/lib/server/account-keys/`** (new): `repo.ts` (`getAccountKey(db, userId)`, `upsertAccountKey(db, userId,
  { publicKey, wrappedPrivateKey, wrapNonce, kdfSalt, kdfParams })` — one row per user, called at first key
  generation and again, with a new salt/wrap/nonce but the **same** key pair, on password change/re-wrap so
  previously sealed results stay openable), `validation.ts` (zod: base64 length/shape checks on every field;
  `kdfParams` bounded to the OWASP-minimum-or-above range named in Architecture notes — never trusting a
  client-supplied scrypt cost outside that range, checklist › "One validator").
- **Routes touched (FN-01's planned tree — this feature extends it, does not fork a second auth flow):**
  - `src/routes/(app)/daftar/+page.svelte` (FN-01's sign-up form) — a progressive-enhancement submit handler:
    if `isAccountKeySupported()` is true, generates the key pair, derives the wrap key from the password **still
    held in the form's own submission**, wraps the private key, and attaches `publicKey`/`wrappedPrivateKey`/
    `wrapNonce`/`kdfSalt`/`kdfParams` as extra hidden fields before the form's normal POST; if unsupported or JS
    is off, the form submits without them. The sign-up action, extended (not duplicated), calls
    `upsertAccountKey` in the same `db.batch` as FN-01's `users`/`user_passwords`/`spaces`/`space_members` insert
    when those fields are present; when absent, no `account_keys` row is created this request
    (`docs/FEATURES.md:230-231`: "if the key is not active yet, results are not stored at all").
  - `src/routes/(app)/masuk/+page.svelte` (FN-01's sign-in form) — on a successful sign-in response (session
    cookie set), if the account has an `account_keys` row (returned by the action) and
    `isAccountKeySupported()` is true, fetches its `wrappedPrivateKey`/`wrapNonce`/`kdfSalt`/`kdfParams`, derives
    the wrap key from the just-submitted password (still in memory, before the form clears it), unwraps the
    private key, and holds it **only in an in-memory module-level variable for this page session** — never
    written to IndexedDB, `localStorage`, or any persisted store this pass (`docs/FEATURES.md:229`: "sign-out
    drops the key from the device" — trivially true when nothing persists it in the first place).
  - `src/routes/(app)/pengaturan/akun/+page.svelte` + `+page.server.ts` (FN-01's account page) — two new
    actions, additive to FN-01's existing `signOut`/`deleteAccount`:
    - `changePassword` (current password + new password + confirm — **FN-01 ships none of this**, see the
      heading-level note above): re-verifies the current password via FN-01's existing password-check function,
      stores the new PBKDF2 hash, and — when the submitting client ran the WebCrypto re-wrap (progressive
      enhancement, same pattern as sign-up/sign-in) — calls `upsertAccountKey` with a fresh salt/wrap/nonce
      around the **same** private key bytes the client decrypted with the old password and re-encrypted with the
      new one, all in one request; when the client could not re-wrap (old browser, JS off), the password still
      changes but the existing `account_keys` row is left as-is, meaning **the next sign-in on an unwrap-capable
      device fails to unwrap with the new password** — surfaced as "Kunci akun tidak bisa dibuka dengan kata
      sandi barumu. Kunci ulang di bawah ini." (and English) with a link to the `activateAccountKey` action below
      (never a silent, confusing failure).
    - `activateAccountKey` ("Kunci dengan akunku," `docs/FEATURES.md:230`, for an account with no
      `account_keys` row yet — e.g. signed up before JS ran, or on an unsupported browser at the time): re-enter
      the current password; the client generates a fresh key pair, wraps it, and the action calls
      `upsertAccountKey` for the first time. Shown only when `getAccountKey(db, userId)` is null for the signed-in
      user; hidden (not just disabled) once a key exists.
- **Dev-only round-trip demonstration (no real producer exists yet, same precedent as FN-11's dev-seed path,
  `docs/features/fn-11-inbox/PRD.md:84-91`):** in `vite dev` or when `devRoutesEnabled` is true
  (`src/lib/server/dev.ts`), `/dev/ui` gains one additional panel: a text field, "Seal" (calls
  `sealToPublicKey` against the signed-in user's own public key fetched from the server), and "Unseal" (calls
  `unseal` against the in-memory unwrapped private key from this session) — proving the whole chain works end to
  end for manual QA before any real feature (FN-15/16) calls it. Entirely absent (not merely disabled) when
  `devRoutesEnabled` is false, matching `/dev/ui`'s own gate (`src/routes/(app)/dev/ui/+page.server.ts:7-9`).
- **i18n:** every new Indonesian phrase ("Ubah kata sandi", "Kata sandi saat ini", "Kata sandi baru",
  "Kunci dengan akunku", "Kunci akun tidak bisa dibuka dengan kata sandi barumu. Kunci ulang di bawah ini.",
  "Kata sandi salah", a success toast for password change and key activation) added to `src/lib/shared/i18n.ts`
  call sites with an English entry in `i18n-en.ts`; the coverage test fails the build if one is missing.
- **UI states:** loading (key generation/derivation runs off the main thread via a dedicated Web Worker so the
  sign-up/sign-in/change-password form shows a spinner rather than freezing — see Architecture notes), empty
  (n/a — no list UI in this feature beyond the dev panel), error (wrong-current-password shows the same inline
  error FN-01's sign-in already uses; an unwrap failure shows the specific "Kunci akun tidak bisa dibuka..."
  copy above, not a generic error), saving (submit buttons disabled/spinner while key generation/wrapping and the
  network request both run), success (the account-key-related UI never claims success before the server confirms
  the `account_keys` row was written, exactly as every other write-confirmation rule in this codebase).

## Out of scope

- **Any real sealed-result producer.** FN-15 (receipt), FN-16 (statement), FN-25 (portfolio screenshot) are the
  features that will actually call `sealToPublicKey` against a real AI-read result; this pass ships the
  mechanism and a dev-only demonstration, not a production caller.
- **Password reset without the old password.** Still deferred per FN-01 (no e-mail provider configured,
  `docs/features/fn-01-accounts/PRD.md:233`); `docs/ARCHITECTURE.md:67`'s own note — "Password reset without the
  old password cannot recover sealed results; the UI says so before reset" — is documented here as the exact
  warning copy a future password-reset feature must show, but no reset flow is built in this pass to show it in.
- **Re-wrapping for every signed-in device simultaneously.** Only the device performing the password change
  re-wraps; any *other* currently-signed-in device simply re-fetches the new wrapped key and re-derives on its
  next sign-in (or the next time it needs to unseal something) — there is no push-based "re-wrap on every
  session" mechanism this pass.
- **Key rotation / revocation** (issuing a brand-new key pair and re-sealing every past result under it) — out
  of scope; "Password change re-wraps the private key" (`docs/ARCHITECTURE.md:67`) keeps the same key pair,
  it does not rotate it.
- **Any server-side storage of the plaintext private key or the user's password**, ever, at any point — the
  server only ever sees and stores the public key and the wrapped (still-encrypted) private key blob.
- **Workers AI / R2 integration for actual file uploads** — this feature's `sealToPublicKey`/`unseal` functions
  are generic byte-sealing primitives; wiring them to an actual upload pipeline (memory-only processing,
  partner-copy deletion and verification) is FN-15/16's job.

## Acceptance criteria

**Key generation and support detection**

1. `isAccountKeySupported()` returns `true` on a runtime whose `crypto.subtle.generateKey({ name: 'X25519' },
   ...)` succeeds, and `false` (never throwing to the caller) on one where it rejects — proven with a mocked
   `crypto.subtle` in both branches, no real browser needed for this unit test.
2. `generateKeyPair()` returns a 32-byte raw public key and a non-extractable-by-default... (the private
   `CryptoKey` itself is never exported except through `wrapPrivateKey`'s own raw export step) — two calls
   produce two different key pairs (fresh randomness, never deterministic).
3. Given sign-up on a key-capable browser with JavaScript, after submitting, an `account_keys` row exists for the
   new user with a non-empty `public_key`/`wrapped_private_key`/`wrap_nonce`/`kdf_salt`/`kdf_params`.
4. Given sign-up with JavaScript disabled, or on a browser where `isAccountKeySupported()` is `false`, after
   submitting, the user account is created exactly as FN-01 already specifies, but **no** `account_keys` row
   exists — the degraded path `docs/FEATURES.md:231` describes ("if the key is not active yet, results are not
   stored at all"), never a failed sign-up.

**Wrap / unwrap round trip**

5. Given a password, a freshly generated key pair, `deriveWrapKey` → `wrapPrivateKey` → `unwrapPrivateKey` with
   the **same** password round-trips to a `CryptoKey` whose raw-exported bytes equal the original private key's
   raw-exported bytes — the core correctness test this feature exists to prove.
6. Given the same wrapped blob and nonce, `unwrapPrivateKey` called with a **wrong** password returns `null`
   (the GCM tag check fails, caught internally) — never a corrupted key, never a silent "looks unwrapped but
   isn't" result (checklist › "Sealed results" › "round-trip test plus a wrong-password test").
7. `wrapPrivateKey` uses a fresh, cryptographically random 12-byte nonce on every call (`crypto.getRandomValues`)
   — two wraps of the same key under the same password produce different `wrapped`/`nonce` byte pairs (no nonce
   reuse, checklist › "Sealed results" › "fresh nonce per seal").
8. `deriveWrapKey`'s scrypt parameters (`kdfParams`) default to at least OWASP's current minimum (`N = 2^15`
   (32,768), `r = 8`, `p = 1`, per the OWASP Password Storage Cheat Sheet's scrypt minimum — the engineer
   re-checks that cheat sheet at implementation time rather than trusting this PRD's number if it has since
   changed, per `CLAUDE.md`'s own instruction never to hard-code a guessed parameter) and run in a dedicated Web
   Worker, not the main thread, so the sign-up/sign-in form's UI stays responsive during derivation.
9. `account_keys.kdf_params` written by a client-supplied value below the OWASP minimum is rejected by
   `validation.ts` server-side (criterion covers a crafted request attempting to weaken a future wrap) — never
   silently accepted.

**Seal / unseal**

10. Given a recipient's public key, `sealToPublicKey(plaintext, publicKeyRaw)` followed by `unseal(sealed,
    privateKey)` (the matching private key, unwrapped via criterion 5) returns bytes identical to the original
    plaintext.
11. Given the **wrong** recipient's private key (a different user's), `unseal` throws rather than returning
    incorrect plaintext — the ECDH shared secret differs, so the derived AES key differs, so the GCM tag check
    fails.
12. Two calls to `sealToPublicKey` with the same plaintext and the same recipient public key produce different
    `ephemeralPublicKey`/`nonce`/`ciphertext` each time (a fresh ephemeral key pair and nonce per seal — never
    deterministic output that would let an observer correlate two sealed blobs of the same content).
13. `sealToPublicKey`/`unseal` never call any D1, R2, or Cloudflare binding directly — they operate purely on
    bytes passed in and out, so a future Worker-side caller (FN-15/16) can call `sealToPublicKey` with a public
    key it fetched itself, with no circular dependency on this feature's own repo module.

**Sign-in unwrap and session handling**

14. Given a user with an existing `account_keys` row signs in on a key-capable browser with JavaScript, the
    client derives the wrap key from the submitted password and unwraps the private key into an in-memory
    variable for that page session — proven by a browser test asserting the dev panel's "Unseal" demonstration
    succeeds immediately after sign-in with no further password prompt.
15. Given the same user signs out, the in-memory unwrapped private key is discarded (a fresh page load after
    sign-out has no unwrapped key available) — `docs/FEATURES.md:229`: "sign-out drops the key from the device."
16. Given the user reloads the page while still signed in (no sign-out), the unwrapped private key is **not**
    automatically available again until the next sign-in — this pass never persists the unwrapped key across a
    reload (stricter than the mirror requires, but consistent with "never written to IndexedDB/localStorage" in
    Scope; a later feature that wants reload-persistence must explicitly add an encrypted-at-rest session store,
    not assumed here).

**Password change and re-wrap**

17. Given a signed-in user submits `changePassword` with the correct current password and a new password meeting
    FN-01's own strength rules, on a key-capable browser with JavaScript, then the PBKDF2 hash updates, the
    `account_keys` row's `wrapped_private_key`/`wrap_nonce`/`kdf_salt` update to new values, and a subsequent
    `unwrapPrivateKey` call using the **new** password and the new wrapped blob successfully recovers the exact
    same private key bytes as before the change (proven by sealing something with the public key before the
    change and unsealing it with the post-change unwrapped private key).
18. Given `changePassword` with an incorrect current password, the action is refused with the same inline error
    FN-01's sign-in already uses, and neither the password hash nor the `account_keys` row changes.
19. Given `changePassword` succeeds but the submitting client could not re-wrap (JS off or unsupported browser),
    the password still changes and the existing `account_keys` row is left untouched; the response includes the
    "Kunci akun tidak bisa dibuka dengan kata sandi barumu" notice (criterion covers this exact degraded case,
    never a silent mismatch the user only discovers later when a sealed result fails to open).
20. Given 20 concurrent `changePassword` submissions for the same account (pre-handoff concurrency probe), when
    they race, then the password/`account_keys` row end in a single consistent state (the last to commit wins,
    `updated_at`-guarded like FN-04/05's own edit-conflict pattern) — never a corrupted half-written wrap.

**"Kunci dengan akunku"**

21. Given a signed-in user with no `account_keys` row, `/pengaturan/akun` shows "Kunci dengan akunku"; given one
    exists, the control is absent entirely (not merely disabled).
22. Given `activateAccountKey` is submitted with the correct current password on a key-capable browser, a new
    `account_keys` row is created (first key generation for this account, per criterion 3's shape) and the
    control disappears on the next render.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

23. `account_keys` rows are reachable only via `getAccountKey(db, userId)`/`upsertAccountKey(db, userId, ...)`
    scoped to `event.locals.user.id` — never a client-supplied user id, and never cross-user readable (a
    pre-handoff probe requests another user's key data and gets the uniform not-found/forbidden response, never
    a 200 with someone else's wrapped key).
24. Every form body on `changePassword`/`activateAccountKey` is read within a size cap and answers 400 or 415,
    never 500, on a malformed or oversized body (reuse FN-01's `src/lib/server/forms.ts` guard).
25. The plaintext password and the derived wrap key never leave the device — a code-search in the hand-off shows
    no network call anywhere in this feature that sends either; only the public key and already-wrapped
    (encrypted) private key blob are ever POSTed.
26. `src/lib/shared/account-key.ts` imports nothing from `src/lib/server` or any Cloudflare binding, and its only
    non-WebCrypto dependency is the one named vetted scrypt library (Architecture notes) — a grep in the hand-off
    proves this, since the module must run unchanged in the browser and (for sealing only) the Worker.
27. Every Indonesian phrase added for this feature has an English entry in `i18n-en.ts`; `npm run test`
    (`src/lib/shared/i18n.test.ts`) fails if one is missing.
28. The dev-only seal/unseal panel is entirely absent (not merely disabled) when `devRoutesEnabled` is false,
    identical to `/dev/ui`'s own existing gate.
29. User-facing error text in this feature never contains a file path, stack trace, row id, or any key material
    (public key, wrapped blob, salt) in a form a screenshot could leak meaningfully.
30. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression test
    (wrap/unwrap round trip, wrong-password unwrap, seal/unseal round trip, wrong-recipient unseal, re-wrap
    preserves the key, concurrent password-change race, degraded no-JS/unsupported-browser path) is shown failing
    on the unfixed code first (checklist › Tests › "Fail-before proof").

## Architecture notes

**Official references checked (per `CLAUDE.md`: re-check official docs before choosing a provider capability)**

- **X25519 `deriveBits` browser support:** Chrome 133+, Firefox 130+, Safari 17+ (all three major engines
  implemented it within roughly the last two years as of this writing) — `isAccountKeySupported()`'s runtime
  feature-detection (criterion 1) is the reason this feature never hard-codes a version check: an older browser
  simply fails the `try`/`catch` probe and degrades per criterion 4, rather than this PRD guessing a cutoff that
  drifts out of date.
- **Cloudflare Workers `crypto.subtle` X25519 support:** `generateKey`/`deriveBits` accept `'X25519'`/`{ name:
  'X25519' }` in the Workers runtime's Web Crypto implementation (BoringSSL-backed) — confirmed against
  Cloudflare's own Web Crypto API docs; `sealToPublicKey` can therefore run inside the app/jobs Workers (for a
  future FN-15/16 caller) using the exact same `src/lib/shared/account-key.ts` functions as the browser, with no
  Worker-specific fork.
- **Scrypt is not part of WebCrypto's `SubtleCrypto` algorithm set** (no browser or Workers runtime implements
  it natively) — this feature names `@noble/hashes`'s `scrypt` implementation as the vetted library: independently
  audited by Cure53 (2022), zero runtime dependencies, explicitly supports Cloudflare Workers, browsers, Node,
  Deno and Bun from the same source, with ongoing fuzzing and provenance-verified releases. Its raw output bytes
  are imported into WebCrypto via `crypto.subtle.importKey('raw', ...)` so every downstream AES-256-GCM operation
  still goes through `SubtleCrypto`, keeping exactly one non-WebCrypto dependency in the whole module (checklist
  › "Sealed results" › "Only WebCrypto/vetted primitives... never invent a scheme").

**Modules touched / added**

- `src/lib/server/db/schema.ts` — add `account_keys` (Drizzle), migration generated into
  `migrations/0011_account_keys.sql`: `account_keys (id pk text, user_id text not null unique references
  users.id, public_key text not null, wrapped_private_key text not null, wrap_nonce text not null, kdf_salt text
  not null, kdf_params text not null, created_at integer not null, updated_at integer not null)`. One row per
  user (`user_id` unique); `upsertAccountKey` updates `wrapped_private_key`/`wrap_nonce`/`kdf_salt`/`kdf_params`
  in place on re-wrap, `public_key` never changes after first generation (same key pair, criterion 17). No
  `deleted_at`/`space_id` — this table is account-level like FN-01's own tables, not space-scoped financial data;
  it is deleted as part of FN-01's existing account-deletion path (`docs/features/fn-01-accounts/PRD.md:125-129`)
  the moment that feature's `db.batch` is extended to include it (a one-line addition to FN-01's delete path when
  this feature lands after it — noted here so the engineer does not forget a user's sealed-result key when their
  account is deleted).
  - `getDb(env.DB)` reused unchanged.
- `src/lib/shared/account-key.ts` (new) — as described in Scope; its only dependency is `@noble/hashes/scrypt`
  (new npm dependency, added to `package.json`) plus the browser/Workers-native `crypto.subtle`.
- `src/lib/server/account-keys/` (new) — `repo.ts`, `validation.ts`, as described.
- `src/routes/(app)/daftar/`, `/masuk/`, `/pengaturan/akun/` — FN-01's planned routes, extended (not duplicated)
  with the account-key generation/unwrap/re-wrap/activation behaviour described in Scope.
- `src/routes/(app)/dev/ui/+page.svelte` (+ its `+page.server.ts`) — one additional dev-gated seal/unseal panel.
- `src/lib/shared/i18n.ts`/`i18n-en.ts` — add every new phrase.
- A new Web Worker module (e.g. `src/lib/shared/account-key.worker.ts`) running `deriveWrapKey`'s scrypt
  computation off the main thread; same-origin module Worker, no CSP change needed — `vite.config.ts`'s `csp`
  block sets no `worker-src` override (`vite.config.ts:13-30`), so a same-origin Worker already falls back to the
  existing `script-src: ['self']` directive.
- No CSP change for `crypto.subtle` itself (not a network-governed API) or for the Web Speech-unrelated nature of
  this feature; `Permissions-Policy` is untouched (this feature asks for no new browser permission).
- Worker: app Worker only this pass (the routes above); `sealToPublicKey`'s Workers-runtime usage is documented
  for FN-15/16's `workers/jobs` callers but nothing in `workers/jobs`/`workers/inbound` calls it yet.

**Reuse / do not duplicate**

- FN-01's existing password-hash verification function is reused by `changePassword`/`activateAccountKey` —
  no second password-check implementation.
- FN-01's `src/lib/server/forms.ts` guard, one i18n table — none reimplemented.
- `sealToPublicKey`/`unseal` are the **only** sealing primitives in the codebase; a later feature (FN-15/16) must
  call them, never hand-roll a second ECDH/HKDF/AES-GCM scheme (checklist › "Sealed results" › "never invent a
  scheme").

## Owner decisions

**Every decision below is auto-accepted per owner instruction 2026-10-08 ("just auto accept your recomm"). No
open questions remain.**

- **A. Unwrapped private key held only in an in-memory page-session variable, never persisted (not even to
  IndexedDB) this pass.** *Trade-off:* a reload mid-session loses the unwrapped key until the next sign-in
  (criterion 16) — stricter than necessary but the safest default; a later feature that wants reload-persistence
  must add its own encrypted-at-rest session store deliberately, not inherit one assumed here.
- **B. Scrypt parameters default to the OWASP-cheat-sheet minimum at implementation time** (named here as
  `N = 2^15, r = 8, p = 1` per the sheet as read for this PRD), re-checked against the live cheat sheet when the
  engineer implements this, not hard-coded from this document if OWASP's guidance has since moved. *Trade-off:*
  higher cost settings would slow sign-up/sign-in further on low-power devices; the OWASP minimum is the
  documented floor, not a performance-optimised choice — a future pass can raise it with a migration to re-wrap
  existing keys if device performance data suggests the floor is already comfortable.
- **C. `@noble/hashes`'s `scrypt` is the named vetted library (not a hand-rolled scrypt, not a different npm
  package).** *Trade-off:* one new runtime dependency is added to the bundle (small — a single hash function
  ships at roughly a few KB gzipped per the library's own published size); the alternative (writing scrypt from
  spec) is exactly the "never invent a scheme" mistake the checklist warns against.
- **D. Key generation/unwrap/re-wrap are progressive-enhancement only — no account key exists for a JS-off or
  unsupported-browser sign-up, and a user on such a browser cannot activate "Kunci dengan akunku" until they use
  a capable one.** *Trade-off:* a small minority of very old browsers/JS-disabled users never get sealed-result
  protection and simply see "results are not stored at all" from whichever future feature needs it
  (`docs/FEATURES.md:231`'s own documented fallback) — this is the mirror's own specified degraded behaviour, not
  a gap this PRD introduces.
- **E. Password reset (forgot password, no old password) remains fully out of scope, carrying FN-01's own
  deferral forward** — the warning copy ("resetting will lock your sealed results") is documented now so whichever
  future feature builds reset does not have to re-derive the correct warning from `docs/ARCHITECTURE.md:67` from
  scratch, but no reset UI exists to show it in yet. *Trade-off:* none new — this is strictly inherited from
  FN-01's own already-accepted deferral.
