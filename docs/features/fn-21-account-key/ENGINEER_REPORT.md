left room or was internally inconsistent.

## Crypto (shared, device and Workers)

- `src/lib/shared/account-key.ts`: WebCrypto only plus `@noble/hashes@2.4.0` (pinned exact, scrypt only).
  - Key pair: X25519 `generateKey`; public key raw (32 B).
  - Wrap: scrypt → AES-256-GCM key (non-extractable), fresh 12-byte nonce per wrap, AD = label ‖ public key.
    The private key is wrapped as **PKCS#8 (48 B)**, not "raw": WebCrypto X25519 private keys export only as
    pkcs8/jwk (the PRD's "raw" is not available). `unwrapPrivateKey` returns `null` on any GCM failure.
  - Seal: ephemeral X25519 → HKDF-SHA256 (salt empty, info = label ‖ ephemeral pk ‖ recipient pk) →
    AES-256-GCM, fresh nonce, AD = header. Envelope v1 `[version][epk 32][nonce 12][ct+tag]`
    (`encodeSealed`/`decodeSealed`, unknown version refused).
  - **Decision:** `unseal(sealed, privateKey, recipientPublicKeyRaw)` takes the recipient public key too (PRD
    named two params) so the recipient key is bound into HKDF, as HPKE does.
  - scrypt parameters: re-checked the live OWASP Password Storage Cheat Sheet 2026-10-08 — the minimum is now
    **N = 2^17, r = 8, p = 1** (128 MiB), not the PRD's 2^15. Allowed range on read/write: r = 8, p = 1,
    dkLen = 32, N a power of two in 2^17..2^18 (upper cap protects the device's memory). Enforced by the shared
    `isAllowedScryptParams`, used by the server validator and by `deriveWrapKey` itself.
  - `@cloudflare/workers-types` spells `deriveBits`' member `$public`; a typed cast (`x25519Algorithm`) keeps one
    source for both type sets (`tsc -p workers/jobs` includes `src/lib/shared`).
- `src/lib/shared/account-key-fields.ts`: transport shape (base64url + params JSON), one encoder/decoder for
  device and server (exact byte lengths, params policy).
- Workers runtime verified: an ad-hoc `wrangler dev` probe worker (scratch, port 8825, not committed) imported
  the shared module: `{"supported":true,"unsealed":"workerd","scryptMs":407,"unwrapOk":true,"wrongNull":true}`.
  Cloudflare's Web Crypto docs list X25519 deriveBits/generateKey/import/export. scrypt is device-side only
  (0.4 s CPU would not fit a Worker request; nothing server-side derives).

## Server

- `src/lib/server/account-keys/{repo,validation,messages}.ts`. **Decision:** instead of one `upsertAccountKey`,
  three guarded writes: `insertAccountKey` (sign-up batch), `activateAccountKey` (INSERT … SELECT … WHERE password
  hash = proven, ON CONFLICT DO NOTHING), `rewrapStatement`/`rewrapAccountKey` (UPDATE only wrap fields, WHERE
  `updated_at` = version AND same `public_key` AND password hash = expected). `public_key` is never updated.
- `src/lib/server/auth/change-password.ts`: one `db.batch` — credential UPDATE guarded on the proven hash (and,
  with a re-wrap, on the key row still at its version + public key), then the key UPDATE guarded on the *new*
  hash. Both or neither; of 20 concurrent changes exactly one commits.
- **Decision (stale key):** a key whose `updated_at` < `user_passwords.updated_at` is *stale* (password changed
  where it could not be re-wrapped). The PRD's "Kunci ulang di bawah ini" links to activation, which it also
  says is hidden once a key exists; activation would also rotate the pair (out of scope). Instead a
  `rewrapAccountKey` action re-locks the **same** key: the device opens it with the earlier password (an input
  with no `name`, never sent) and re-wraps under the current one; the server proves only the current password.
- **Decision (material only after a password proof):** the wrapped key reaches a device only in the response to
  a password proof — sign-in with `withKey=1`, or `/pengaturan/akun?/keyMaterial` — never in a loader (the
  account page load returns only `{ exists, stale }`, `/dev/ui` only the user's own public key).
- Routes: `/daftar` (optional key fields into the sign-up batch; malformed → 400, nothing created),
  `/masuk` (`withKey=1` → `{ signedIn, next, accountKey }` instead of the redirect), `/pengaturan/akun`
  (`keyMaterial`, `changePassword`, `activateAccountKey`, `rewrapAccountKey`), `/dev/ui` load.

## Device

- `src/lib/ui/account-key/device.ts`: the opened key (non-extractable) is a module variable for the page session
  only — never IndexedDB/localStorage; dropped by reload, sign-out (`dropDeviceKey` + the existing full-load
  `location.assign` + Clear-Site-Data) and account deletion. scrypt runs in `derive.worker.ts` (module Web
  Worker, built to `_app/immutable/workers/`, same-origin so `script-src 'self'` covers it; no CSP change).
- Sign-up/sign-in/change-password/activation/re-lock are progressive enhancement (`use:enhance` submit
  functions); without JS or X25519 sign-up creates no key, sign-in redirects as before, change-password changes
  the password and the answer shows the stale notice. A key that does not open at sign-in sends the user to
  `/pengaturan/akun`, which explains it.
- UI: `AccountKeySection.svelte`, `ChangePasswordSection.svelte` (states: saving spinner, inline refusals,
  success only after the server's answer), `SealDemo.svelte` on `/dev/ui` (absent unless dev routes).
- Password reset is still not built; the account page states "Lupa kata sandi berarti hasil yang terkunci tidak
  bisa dibuka lagi…" as the copy a future reset must show.

## Gaps and notes

- No real sealed-result producer yet (FN-15/16), per the PRD; the mechanism is proven by tests and the dev panel.
- The password itself still goes to the server at sign-in/change (FN-01's PBKDF2 auth); the scrypt wrap key and
  the plain private key never do. A malicious server seeing the password could unwrap — inherent to deriving
  both from one password; noted for the red team.
- A browser that kills the derive Worker without an `error` event would leave the form spinning (no timeout).
- Changing the password does not revoke the user's other sessions (FN-01 behaviour, not in this PRD).
- Possible e2e slowdown/flakiness: every e2e sign-up now spends ~0.3–0.5 s CPU and 128 MiB on scrypt.

## Cycle 2 (red team abb18c2 FAIL, QA 6d3b7d6 PASS note)

Rebased onto `main` 9c77de9 (FN-14 voice; only conflict `i18n-en.ts`, both blocks kept). Main still ends at 0009,
so `0011_account_keys` stays chained to the 0009 snapshot. **0011 was regenerated** (new `key_check` column); it
was never applied outside local/e2e D1 and is unmerged, so no applied migration was edited.

- **M1 fixed** — `src/lib/server/auth/change-password.ts`: the same `db.batch` revokes every other session of the
  user and tombstones their push subscriptions (`removeOtherSessionSubscriptions`, `src/lib/server/push/repo.ts`),
  both guarded on the *new* hash, so they run only if the change committed. The current session stays signed in.
  Tests: two sessions plus push rows for both and for another user → the other session is refused by `hooks.server`
  (303 to `/masuk?next=…`), and only its subscription is tombstoned; a refused change revokes nothing; e2e device B →
  `/masuk` after A changes the password.
- **L1 fixed** — key confirmation: `keyCheck(priv, pub)` = HKDF-SHA256(X25519(priv, own pub)), sent at every key
  write and stored as `account_keys.key_check` (never returned to clients). Every re-wrap (password change and
  re-lock) must present the stored value, which shows the device opened the current wrap. A re-lock is accepted
  only while the key is stale (`updated_at < user_passwords.updated_at`, in the guarded UPDATE). Remaining
  limit: someone holding the session *and* the current password can still open the key, so they can still write
  a bad wrap; that follows from the threat model.
- **L2 fixed** — `device.ts`: `announceSignOut` (BroadcastChannel `financer-session`) on sign-out/deletion;
  `watchSessionEnd` in the `(app)` layout drops the key on another tab's broadcast, or on `visibilitychange` when
  `/pengaturan/akun/__data.json` answers 401 or a redirect; the `(auth)` layout and a 401 error page drop it too.
  Unit tests (broadcast, visibility live/offline/ended, hidden/no-key no request); e2e second tab signs out → first
  tab's key gone without reload.
- **L3 fixed** — `proveCurrentPassword` counts `account-password` per client (`overAttemptLimit`) and per user
  (new `overUserAttemptLimit`) before deriving; 429 "Terlalu banyak percobaan…". Tests: 21st per client and 21st
  per user (rotating addresses) → 429.
- **L4 fixed** — `_headers`: `/_app/immutable/workers/*` → `Content-Security-Policy: default-src 'none';
  base-uri 'none'` (the built worker is self-contained). Unit test on `_headers`; e2e fetches the worker URL the
  page loaded and asserts the header.
- **QA note fixed** — `deriveWrapKeyOffThread` times out after 30 s (`KeyDerivationTimeout`, worker terminated);
  account-page forms show "Kunci akun terlalu lama diproses di perangkat ini. Coba lagi."; sign-up degrades to no
  key; sign-in lands on the account page. Unit test with fake timers.
- Fail-before proof: the new tests were run against the cycle-1 tree (`git archive` of the cycle-1 commit into

## Cycle 3 (red-team re-check 254c02f PASS, N1/N2)

- **N2 fixed** — the column is now `account_keys.key_check_hash`: SHA-256 (hex) of the canonical base64url key
  check, computed in `readAccountKeyForm` (now async), so the raw check never reaches the repo. Re-wrap actions
  first compare digests with `equalConstantTime` (`keyCheckMatches`, repo.ts); the guarded UPDATEs also compare the
  digest in SQL, so a race cannot slip past. `0011_account_keys` was regenerated in place (applied nowhere remote,
  `prevId` still the 0009 snapshot). Test written first, failing on cycle 2 (`no such column: key_check_hash`):
  the stored value equals SHA-256 of the check, and replaying the stored digest as a key check → 409, nothing
  written. Gates: check 0/0, lint clean, vitest 94 files / 1366 tests, build OK; e2e `account-key.spec.ts` 15 passed.
- **N1 accepted, documented** — the per-user `account-password` budget (20 per 10 min) counts correct passwords
  too, so someone with a stolen session can use it up and block "Ubah kata sandi" until the window ends. That adds
  nothing new: since FN-01, a session holder can already lock the account with wrong passwords (account lockout).
  A future "sign out all devices" must not depend on this budget.
