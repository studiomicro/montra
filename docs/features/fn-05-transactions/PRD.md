## Goal

The main journey's steps "record by voice" and "see Beranda" both terminate in one thing: a row in a ledger that
belongs to a space, has a category and a wallet, and shows up the same way wherever its number is summed. FN-05
is that ledger plus the one screen (Riwayat) a user checks when they want to know exactly what happened; FN-06 is
the small, editable vocabulary (15 presets, renamed, hidden or added to) every transaction's category comes from.
Until this pair ships, `/kekayaan` has no real balances (FN-04 passes `0` for every wallet), Beranda and Laporan
have nothing to total, and the "add a wallet → record by voice" journey has no destination for what voice, receipt
or Gmail will later produce as drafts — this pass builds the destination (manual entry only) and the one shared
aggregate module every later capture path and every later insight screen (FN-07 safe-to-spend, FN-08 Beranda,
FN-09 Laporan) must call unchanged, so "Beranda total = Riwayat total for the same filter" is true by construction,
not by coincidence.

## Out of scope

- Every non-manual capture path (`source` values `gmail`, `voice`, `receipt`, `statement`, `spreadsheet`, `csv`,
  `slack`) — FN-14/FN-15/FN-16/FN-17/FN-18/FN-19. This pass ships the `source` column and its dedupe-key unique
  index (see Architecture notes) so those features plug in without a second migration, but writes only ever
  `source = 'manual'` and `dedupe_key = NULL`.
- Foreign currency (`original_amount_minor`/`original_currency`, day's-rate conversion) — FEATURES.md FN-05
  mirror lists it, but every wallet this pass is assumed single-currency for its own transactions: a
  transaction's `currency` is always its wallet's `currency` (no independent currency field on the form), and a
  transfer between wallets of different currencies is rejected (Owner decision E). Real FX conversion is deferred
  to whichever capture feature first needs it.
- Attached photo, payment method, recurrence, tag, reference number fields (FEATURES.md FN-05's full field list)
  — `title`, `note`, `category`, `wallet`, `date`/`time` only this pass; the schema does not block adding the
  rest later without a breaking change (new nullable columns).
- "Badge 'Tercatat' on auto-captured rows" (FEATURES.md FN-05) — the `StatusTag` component exists
  (`src/lib/ui/kit/StatusTag.svelte:1-28`) and is reused as-is for a future captured source, but nothing in this
  pass sets it, since nothing this pass is auto-captured.
- Budgets, safe-to-spend, Beranda, Laporan screens themselves (FN-07/08/09) — this feature ships the aggregate
  module they must call, not their UI.
- Drafts inbox / review states (FN-11) — manual entries are saved directly, never held for review.
- Multi-select category/wallet filters (Owner decision B — single-select this pass); hard delete of a custom
  category (Owner decision C — hide only); offline write queue / IndexedDB (explicit owner decision, tracked as a
  follow-up item in `docs/TASKS.md` when this feature lands, not built here).
- A `/pengaturan` index page or nav entry to `/pengaturan/kategori` (Owner decision G).
- Recategorising or re-walleting many transactions at once (bulk edit) — FN-11's "Atur kategori"/"Atur dompet"
  bulk actions are a drafts-inbox feature, not built here.

## Acceptance criteria

**Categories (`/pengaturan/kategori`, FN-06)**

1. Given a space with no `categories` rows yet, when any route in this feature loads for that space, then
   `ensurePresetCategories` seeds exactly 15 rows (10 `kind = 'expense'`, 5 `kind = 'income'`) in one guarded
   `db.batch`, one row per `CategoryKey` from `src/lib/ui/kit/category.ts:3-19`, with default `name`s matching the
   FEATURES.md mirror list (`docs/FEATURES.md:72-75`) exactly, including `lain` seeded as `name = 'Pemasukan
   Lain'` (`kind = 'income'`) — not the kit's generic UI label `'Lainnya'` used elsewhere for wallet types.
2. Given two concurrent first-loads of the same just-created space (pre-handoff concurrency probe), when they
   race, then exactly 15 category rows exist afterward, never 30 and never a unique-constraint 500.
3. Given `/pengaturan/kategori`, when it loads, then every non-hidden category appears grouped by `kind`, each
   row showing its `CategoryTile` (icon/colour from `tileKey`) and current `name`; a loading skeleton while the
   load runs and a retry state on failure.
4. Given the "Tambah kategori" action with a name (1–40 chars) and a chosen tile slot, when submitted, then a new
   `categories` row is created with `is_preset = false`, `is_hidden = false`, and it appears in the list and in
   the compose form's category picker without a page reload, and still after a full reload.
5. Given a rename of any category (preset or custom) to a new name, or a change of its `tileKey` to a different
   one of the 15 slots ("icon changeable", FEATURES.md FN-06 mirror), when submitted, then the row updates in
   place; every transaction already pointing at it shows the new name/icon on its next render (no denormalised
   copy of the name stored on `transactions`).
6. Given the "Sembunyikan" action on any category, when submitted, then `is_hidden = true`; it stops appearing in
   the compose form's picker and in `/pengaturan/kategori`'s default view, but a transaction already using it
   still renders its tile and name correctly in Riwayat and in its own edit page (the edit page's picker includes
   the transaction's current, now-hidden category as an already-selected, non-removable-from-this-save option).
7. Given "Tampilkan" on a hidden category, when submitted, then `is_hidden = false` and it reappears in pickers.
8. Given the name field contains control or zero-width characters or exceeds 40 characters, when submitted, then
   it is stripped/capped before storage and a validation error is shown if the result is empty (checklist ›
   Access and privacy › "Untrusted text").
9. No action in this feature hard-deletes a `categories` row (`deleted_at` is never set by this pass — Owner
   decision C); the column exists for a later pass that adds delete-when-unused.

**Create a transaction (`/riwayat/baru`, FN-05)**

10. Given the compose form with `type = 'expense'` or `'income'`, a wallet, a category of the matching `kind`, an
    amount, and `occurredOn` defaulted to `wibTodayString()`, when submitted, then one `transactions` row is
    written with `amount_minor` stored as a **positive integer magnitude** (never negative — the sign convention
    for this schema, decided once here per checklist › Money and dates › "Sign convention"), `currency` copied
    from the chosen wallet, `source = 'manual'`, `dedupe_key = NULL`, and the user is returned to `/riwayat` where
    the new row appears without a further reload.
11. Given the same request, when the full page is reloaded, then the new transaction is still present and in the
    correct day group — persisted state survives reload.
12. Given `type = 'transfer'`, a "Dari dompet" and a "Ke dompet" that are different wallets in the current space
    and share the same `currency`, when submitted, then one `transactions` row is written with `category_id =
    NULL`, `wallet_id` = the source, `transfer_to_wallet_id` = the destination; it never counts toward
    `periodTotals`'s `inMinor` or `outMinor` (criterion 24) and `walletTransactionsSums` debits the source and
    credits the destination by the same magnitude (criteria 27–28).
13. Given a transfer where the two wallets have different `currency` values, when submitted, then the action is
    refused with a field error ("Transfer antar mata uang berbeda belum didukung" / English) and no row is
    written (Owner decision E).
14. Given a transfer where "Dari dompet" and "Ke dompet" are the same wallet, when submitted, then the action is
    refused with a field error and no row is written.
15. Given an amount of zero or a non-numeric amount field, when submitted, then the action fails with a field
    error (`digitsToMinor`-based, never `parseFloat` on money) and no row is written.
16. Given a wallet or category id that does not belong to the current space (crafted request), when submitted,
    then the action is refused with the uniform not-found/forbidden response of `requireSpaceAccess` — never a
    500, never a row written against another space's wallet or category.
17. Given `occurredOn` left at its default and no time entered, when submitted, then the stored `occurred_at` is
    the server's current UTC instant at save time and `occurred_on` is exactly the WIB date the form showed —
    the two are independent; omitting the time never changes which day the transaction is bucketed into (Owner
    decision F).
18. Given a title or note containing control or zero-width characters or exceeding their length caps (80/500),
    when submitted, then they are stripped/capped before storage (checklist › Access and privacy › "Untrusted
    text").
19. Given JavaScript is disabled, when the compose form is submitted with whatever values are present in its
    native inputs (date/amount/title/note; `Segmented`/icon-sheet pickers need JS to change their bound value,
    the same accepted limitation FN-04 already has for its wallet-type `Segmented`,
    `docs/features/fn-04-wallets/PRD.md:129`), then the POST still completes as a normal form submission — it
    never 500s and either saves with the visible defaults or shows a normal validation error.

**Edit and delete (`/riwayat/[id]/edit`)**

20. Given an existing transaction opened for edit, when any field changes and it is submitted with the
    `updated_at` the edit page loaded, then the row updates, `updated_at` advances, and Riwayat reflects the
    change only after the server confirms.
21. Given two tabs open the same transaction for edit (pre-handoff "two tabs / stale forms" probe), when both
    submit with the same stale `updated_at`, then the second is refused with "Berubah sejak terakhir dimuat" (and
    English) — the exact phrase FN-04 already uses, not a re-keyed duplicate.
22. Given "Hapus" on a transaction (with a confirm step), when submitted, then `deleted_at` is set (tombstone,
    content-free per `CLAUDE.md`), `seq` advances, and it disappears from Riwayat and from every total
    (`periodTotals`, `walletTransactionsSums`) immediately after the server confirms; there is no undo in this
    pass (manual entries only — "a deleted captured row is never recreated from the same source" does not apply
    yet since nothing is captured).
23. Editing or deleting a transaction never changes its `source` or `dedupe_key` (both are write-once at create
    time) — stated now so no later capture-review feature is tempted to "fix" a manual row into a captured one
    by editing those columns in place.

**Riwayat list, filters, search and the totals contract**

24. Given any combination of `type`/`period`/`category`/`wallet`/`q` filters, when `/riwayat` loads, then the
    header shows `trf('{n} transaksi · keluar {out}', …)` (Semua or Keluar chip active) or the Masuk-only
    equivalent (Masuk chip active), where `n` and `out`/`in` come from one call to `periodTotals(db, spaceId,
    filter)` with that exact filter — never a client-side re-sum of the rendered list. A unit test calls
    `periodTotals` directly against seeded fixture rows and asserts the number equals the manual sum of the same
    rows, proving the "Beranda total = Riwayat total for the same filter" rule (checklist › Money and dates ›
    "Totals reconcile") holds for the one function every later screen must reuse unchanged.
25. Given the Semua chip, when the list renders, then transfers appear in the day groups (styled per the
    `TransactionRow` `kind='transfer'` addition) but contribute `0` to both `inMinor` and `outMinor` everywhere
    they are shown or totalled.
26. Given the Keluar or Masuk chip, when active, then transfers are excluded from the list entirely (not just
    from the totals) — the chip labels mean "expense"/"income" rows only, matching FEATURES.md's "tabs Semua /
    Keluar / Masuk" pattern already used for statement import (`docs/FEATURES.md:162`).
27. Given a wallet with `openingBalanceMinor` and some mix of expense, income and transfer rows pointing at it,
    when `walletTransactionsSums` runs, then its entry equals `Σincome − Σexpense − Σ(transfer out) +
    Σ(transfer in)` for that wallet, computed in one grouped SQL query (checklist › Data access › "Bounded
    work" — aggregated in SQL, not by loading every row), and `walletBalanceMinor(wallet, sums[wallet.id])`
    (`docs/features/fn-04-wallets/PRD.md:37-39`) matches that sum exactly.
28. Given `/kekayaan` loads after this feature lands, when a wallet has transactions, then its shown balance is
    `openingBalanceMinor + walletTransactionsSums(...)[wallet.id]`, not just the opening balance — the seam FN-04
    left open (`docs/features/fn-04-wallets/PRD.md:72-73`) is now filled, and `formatMoney`/`formatMoneyCompact`
    (`src/lib/shared/money-format.ts:36,62`) still render it, unchanged.
29. Given a search term, when submitted via the `GET` search form, then matching rows are found with
    `instr(lower(title), lower(?)) > 0 OR instr(lower(note), lower(?)) > 0` — never `LIKE`/`GLOB` (checklist ›
    Data access › "LIKE and GLOB patterns" — D1 rejects a pattern over 50 bytes; `instr()` has no such cap). A
    regression test runs a 60+ character search term and asserts no D1 error, proving why `instr()` was chosen.
30. Given a search or filter combination, when the query runs, then it is always scoped by `space_id` and
    bounded by the active period plus a page `LIMIT` (Owner decision A) — never an unbounded table scan
    (checklist › Data access › "Bounded work").
31. Given more rows exist than the page size, when "Muat lebih banyak" is pressed, then the next bounded page
    appends via the same `cursor`-based query, never re-fetching or duplicating already-shown rows.
32. Given the WIB-boundary vectors (checklist › Money and dates › "WIB dates"), when a transaction is created at
    23:30 WIB on the last day of a month and another at 00:30 WIB on the first day of the next month, then their
    `occurred_on` values fall in the correct respective months and each appears in the correct month's
    `periodTotals`/day group — never off by one UTC day.
33. Given no transactions exist in the current space, when `/riwayat` loads, then one `EmptyState` copy shows
    ("Transaksi yang kamu catat muncul di sini.", already present at
    `src/routes/(app)/riwayat/+page.svelte:11`, reused for the true-empty case); given transactions exist but the
    active filter matches none, then a second, distinct "no results for this filter" copy shows instead — the two
    cases are never conflated.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

34. Every `+page.server.ts` load and action under `/riwayat`, `/riwayat/baru`, `/riwayat/[id]/edit` and
    `/pengaturan/kategori` resolves the space through `requireSpaceAccess` using `event.locals.user` — never a
    client-supplied `spaceId`; a transaction, category or wallet id from a different space gets the identical

## Owner decisions

**Answered by the owner 2026-10-08: accept every proposed default below as written.**


The following are genuinely open for this pass; proposed defaults are used unless the owner overrides them
before build.

- **A. Riwayat page size.** *Proposed default:* 50 transactions per page, cursor-paginated, "Muat lebih banyak."
  *Trade-off:* a very active month needs several taps to see everything; the alternative (load everything in the
  period at once) risks an unbounded scan the checklist explicitly forbids.
- **B. Filter cardinality.** *Proposed default:* single-select category and single-select wallet filters this
  pass (one category or "Semua kategori," one wallet or "Semua dompet"). *Trade-off:* a user cannot filter "Kopi
  or Makan & Minum" at once; multi-select would cost extra UI (checkbox list instead of a radio-style
  `GroupList`) for a capability the main journey does not yet need.
- **C. Custom category deletion.** *Proposed default:* hide only, never hard-delete, even for an unused custom
  category (criterion 9). *Trade-off:* a mistakenly-added custom category sits hidden forever rather than
  disappearing from the `/pengaturan/kategori` list entirely; the alternative (delete when zero transactions
  reference it) is a reasonable later addition but needs a reference-count guard this pass skips for time.
- **D. Search scope.** *Proposed default:* `title` and `note` only (criterion 29). *Trade-off:* searching "Gaji"
  will not surface a transaction titled "Oktober" merely because its category is Gaji; matching by category or
  wallet name is a plausible later addition once there is evidence users expect it.
- **E. Cross-currency transfers.** *Proposed default:* rejected this pass — both wallets in a transfer must share
  `currency` (criterion 13). *Trade-off:* a user with an IDR cash wallet and a USD wallet cannot log moving money
  between them as one transfer until FX-aware transfers exist (no ETA set); they would need two manual expense/
  income rows instead, which is not ideal but not blocked.
- **F. Default time when omitted.** *Proposed default:* the server's current UTC instant at save time
  (`occurred_at`), fully independent from the user-chosen `occurred_on` WIB date (criterion 17). *Trade-off:*
  none functionally (bucketing is unaffected), but same-day rows sort by "when I happened to save it," not by
  any real-world time, until the user fills in a time.
- **G. Where category management lives.** *Proposed default:* ship `/pengaturan/kategori` now, reachable only
  from a "Kelola kategori" link inside the compose form's category picker, since `/pengaturan` itself is still
  the `[stub=stub]` placeholder (`src/params/stub.ts:1`) with no index page or nav entry to a sub-route yet.
  *Trade-off:* a user who wants to manage categories without first opening the add-transaction sheet has no
  direct path there until a real `/pengaturan` index page exists (whichever feature builds it, likely alongside
  FN-01's `/pengaturan/akun` or FN-12 feature toggles).
