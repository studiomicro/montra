# FN-13 Install and notifications (PWA) — PRD

Catalog entry: `docs/FEATURES.md` › FN-13 (line 110-117). Phase: 1 — Core ledger. Tracker: `docs/TASKS.md` ›
Phase 1 › "... FN-12 Feature toggles · **FN-13 PWA and push**" (`docs/TASKS.md:61-62`). Risk tier: **Medium**
(new service worker + Web App Manifest interacting with the locked CSP, a new user-scoped table, and a
WebCrypto-based Web Push send path that must run inside the Workers runtime — no auth/session or money schema
changes, but several new browser-platform surfaces that are easy to get subtly wrong).

Owner decisions already fixed before this pass (do not re-litigate): server-first in D1, signed-in only for
anything user-scoped (push subscriptions); install/manifest/service-worker/in-app-browser-detection work for
everyone, signed in or not, since installability is a browser capability, not an account feature. Migration
number is **`0009`** (chain: FN-01 `0001` … FN-11 Drafts `0007`, FN-12 Feature flags `0008`, this feature `0009`
— renumber at merge if the actual landing order differs).

**Offline write queue: explicitly not built here.** The brief's own framing applies: this feature ships a
**read-only offline shell** (cached app chrome + static assets + one offline fallback page) — no IndexedDB write
queue, no queued-then-synced mutation. That remains FN-02's deferred scope, carried from every prior Phase 0/1
PRD's "no guest mode / local-first sync this pass" decision.

## Goal

The main journey's steps 2–4 (add a wallet, record by voice, see Beranda) only repeat daily if the app is easy
to open — and `docs/PRD.md` §7 already requires it be "installable PWA" with the main journey assuming a home-
screen icon by the time Gmail capture and push notifications matter (FN-19/FN-24). Today there is no
`static/manifest.webmanifest`, no service worker, and no push-subscription storage anywhere in the repo — a
visitor on Android Chrome or iPhone Safari has no install prompt, no offline shell if a page load drops, and no
way to opt into "Beri tahu di perangkat ini" even once a later feature has something worth notifying about.
FN-13 ships exactly that platform floor: installable, update-without-a-download, works when you open it with a
flaky signal, and the one `PushSubscription` round trip every later notification feature (FN-19, FN-24) will
send through.

## Acceptance criteria

**Manifest and installability**

1. Given any visitor (signed in or not), when the app loads, then `<link rel="manifest"
   href="/manifest.webmanifest">` resolves to a valid Web App Manifest with `display: 'standalone'`,
   `start_url: '/'`, `scope: '/'`, and three icon entries (`192`, `512`, `512 maskable`) that each 200 — a
   browser's own installability checks (Chrome's "Add to Home Screen" eligibility) pass against this manifest.
2. Given Android Chrome fires `beforeinstallprompt`, when the app's own "Instal aplikasi" button (shown only
   then) is pressed, then the captured event's `.prompt()` is called and the resulting `userChoice` is not
   assumed — the button disappears only after the browser's own prompt resolves, not immediately on click.
3. Given iOS Safari (which never fires `beforeinstallprompt`), when `/pengaturan/instal` loads, then it shows
   the Bagikan › Tambah ke Layar Utama steps instead of any install button, and once installed and reopened
   from the home screen, `display-mode: standalone` is detected and "Sudah terpasang" shows instead of the
   instructions.
4. Given a desktop browser on `/pengaturan/instal`, when the page renders, then a QR code encoding the current
   `url.origin` is shown, generated client-side with no network request to any third-party QR service.

**Service worker, caching and updates**

5. Given a first visit, when the service worker's `install` event fires, then the compiled app-shell bundle and
   every static asset (manifest, icons, `offline.html`) are cached under one `version`-keyed Cache Storage
   entry.
6. Given a deploy changes `version`, when the new service worker's `activate` event fires, then every cache
   from a previous `version` is deleted and the new shell is served on the next navigation — no separate "an
   update is available, tap to download" step the mirror explicitly says there should not be
   (`docs/FEATURES.md:115`).
7. Given the device goes offline and a navigation's network request fails, when the service worker's `fetch`
   handler runs, then the cached `offline.html` renders instead of the browser's own default offline error page;
   given the device is online, every navigation is served network-first (never a stale cached page shown while
   online).
8. Given a signed-in user's own data routes (`/`, `/riwayat`, etc.), when the service worker intercepts their
   `fetch` requests, then it never caches the response — only the static app-shell and `offline.html` are
   cached; a regression test asserts the service worker's cache keys never include an `/api/` path or a
   data-bearing page response (checklist › Capture and AI adjacent principle, "no upload persistence", applied
   here as "no silent data caching").
9. Given `vite dev`, when the app loads, then no service worker is registered (`!dev` guard) — local development
   never fights a stale cached bundle.
10. Given the service worker registration call, then it is never an inline `<script>` in `app.html` — it runs
    from the app's own bundled JS (`src/routes/+layout.svelte`'s component script), so CSP's
    `script-src: ['self']` (`vite.config.ts:18`) needs no `'unsafe-inline'`/hash addition for it.

**In-app browser detection**

11. Given `detectInAppBrowser(ua)` is called with a known Instagram, TikTok or WhatsApp in-app-browser user
    agent string, then it returns the matching key; given any ordinary browser UA (including Chrome, Safari,
    Firefox, Edge desktop and mobile), it returns `null` — a table of real captured UA strings for the three
    apps is the regression fixture, not a guessed pattern.
12. Given `detectInAppBrowser` returns non-`null`, when the root layout renders, then `InAppBrowserNotice` shows
    OS-appropriate "open in your browser" wording and no install button is offered (none of these in-app
    browsers support PWA install); dismissing it hides it for the rest of that session only.

**Push subscriptions (`/pengaturan/notifikasi`)**

13. Given `isPushConfigured()` is false (no VAPID keys set), when `/pengaturan/notifikasi` loads, then the
    toggle renders disabled with "Belum dikonfigurasi" (and English) and no `Notification.requestPermission()`
    call is ever made — see Prerequisites.
14. Given `isPushConfigured()` is true and the user turns the toggle on, when the browser grants permission and
    `PushManager.subscribe()` succeeds, then the subscription's `endpoint`/`p256dh`/`auth` are posted to action
    `subscribe`, one `push_subscriptions` row is written (`user_id = locals.user.id`), and the toggle shows "on"
    only after the server confirms the write — a granted browser permission with a failed server write is shown
    as off/error, never a false "on".
15. Given the same device's subscription already exists (re-toggling on after reinstalling, or two tabs
    subscribing), when `subscribe` runs again with the same `endpoint`, then the existing row is updated in
    place (unique on `endpoint`), never duplicated.
16. Given the toggle is turned off, when `unsubscribe` runs, then the stored row for that `endpoint` is
    tombstoned (`deleted_at` set) and the client's own `PushManager.unsubscribe()` is called so the browser
    stops holding a subscription the server no longer has a use for.
17. Given an iOS Safari device not running in standalone mode, when `/pengaturan/notifikasi` loads, then the
    toggle is replaced by the "install to the home screen first" message (and English) and no permission prompt
    is attempted — matching the iOS 16.4+/home-screen-icon requirement (`docs/FEATURES.md:116`).
18. Given `devRoutesEnabled` is true and "Kirim notifikasi uji" is submitted, then `sendPushNotification` is
    called for every active subscription of the signed-in user and the result ("sent"/"expired" per
    subscription) is shown; an `'expired'` result removes that subscription row automatically (criterion 19).
    Given `devRoutesEnabled` is false, this action answers 404 — never reachable in a deployed environment
    without `DEV_ROUTES=1`.
19. Given a push send returns a 404/410 from the push service (the browser revoked the subscription without
    telling the server), then `removeSubscription` tombstones that row before the send path returns — a dead
    endpoint is never retried on a later send.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

20. Every load and action under `/pengaturan/notifikasi` resolves the acting user from `event.locals.user` —
    `/pengaturan/instal` requires no session (works signed out, matching criterion 3–4's "any visitor" framing).
21. A pre-handoff probe posts another user's `endpoint` value to `unsubscribe`; the action is refused (the
    query is scoped `WHERE user_id = locals.user.id AND endpoint = ?`, so a foreign endpoint matches nothing) —
    no cross-user tombstoning is possible.
22. Every form body on `subscribe`/`unsubscribe`/`sendTestPush` is read within a size cap and answers 400 or
    415, never 500, on a malformed or oversized body (reuse FN-01's `src/lib/server/forms.ts` guard).
23. Every Indonesian phrase added for this feature (outside `offline.html`, which is exempt by construction)
    has an English entry in `i18n-en.ts`; the coverage test fails the build if one is missing.
24. Touch targets ≥ 44 px (the reused `Toggle`, the install button, the dismiss control); WCAG AA contrast in
    both themes; focus returns correctly when the in-app-browser notice is dismissed.
25. User-facing error text never contains a file path, stack trace, row id, VAPID key material, or raw push
    endpoint.
26. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression
    test (manifest validity, cache-key scope, in-app-browser UA fixtures, `isPushConfigured` false-path,
    endpoint-upsert-not-duplicate, expired-subscription self-clean, cross-user unsubscribe probe) is shown
    failing on the unfixed code first (checklist › Tests › "Fail-before proof").
