## Goal

The "spreadsheet switcher" user (`docs/PRD.md:26`) has years of records in a spreadsheet or in Money Manager and
will not re-type them one at a time. `docs/FEATURES.md:181-183` is explicit that CSV import must work from two
fixed column shapes, create whatever categories/wallets/tags a row names rather than rejecting unknown ones, skip
transfer rows, and save directly with no per-row review screen — the opposite of FN-16's heavier "Tinjau impor"
flow, and a simpler, faster on-ramp that needs neither an AI key nor a connection partner to ship. FN-18 also
builds the one `import_batches` table every later import feature (FN-16 statement, FN-17 spreadsheet, FN-19's
look-back) will reuse for its own "undo removes every transaction of that import" promise
(`docs/FEATURES.md:163`), rather than each inventing its own batch-and-undo bookkeeping.

## Scope

- **Migration `0010`** (`migrations/0010_csv_import.sql`, generated by `drizzle-kit generate`, applied only
  through `npm run db:migrate:local`):
  - New table `import_batches` (columns under Architecture notes) — shaped for reuse by FN-16/17/19 later
    (`source` check includes values this pass never writes, same precedent as FN-05's `dedupe_key` column being
    schema-ready before any real capture path used it,
    `docs/features/fn-05-transactions/PRD.md:338-341`).
  - `ALTER TABLE transactions ADD COLUMN import_batch_id TEXT REFERENCES import_batches(id)` (nullable), plus
    four more nullable columns FN-05's own PRD explicitly anticipated adding later without a breaking change
    (`docs/features/fn-05-transactions/PRD.md:143`: "the schema does not block adding the rest later without a
    breaking change (new nullable columns)"): `payment_method TEXT`, `recurrence TEXT`, `tag TEXT`,
    `reference TEXT`. Index `(space_id, import_batch_id)` for the undo query.
- **`src/lib/shared/csv.ts`** (new, pure, no D1/Workers/DOM dependency — runs unchanged in the browser bundle for
  the instant client-side preview and in the app Worker for the authoritative server-side import, per `CLAUDE.md`
  › "shared domain code... so the client and Worker run the same logic"):
  - `parseCsv(text: string): string[][]` — quote-aware (RFC 4180-style: a quoted field may contain the
    delimiter, a newline, or an escaped `""`), auto-detects comma vs. semicolon from the header row
    (`docs/FEATURES.md:180`: "comma or semicolon separators").
  - `detectCsvFormat(headerRow: string[]): 'template' | 'money_manager' | null` — matches the fixed header sets
    of both formats (case-insensitive); `null` when neither matches (the UI then asks the user to pick one
    explicitly rather than guessing).
  - `mapTemplateRow(row, headerIndex): RawCsvTransaction | SkipReason`, `mapMoneyManagerRow(row, headerIndex):
    RawCsvTransaction | SkipReason` — one mapper per format, each returning either a normalised intermediate
    shape (`date`, `type`, `title`, `amountText`, `currency`, `categoryName?`, `walletName?`, `paymentMethod?`,
    `recurrence?`, `tag?`, `notes?`, `reference?`) or a typed reason the row is skipped (`'transfer'`,
    `'missing_date'`, `'missing_amount'`, `'unparseable_amount'`, `'unsupported_currency'`).
  - `parseCsvDate(text: string): string | null` — the two fixed absolute formats named by FEATURES.md
    (`docs/FEATURES.md:180`): ISO `YYYY-MM-DD` (returned verbatim, it is already a WIB-style date string) and
    `DD/MM/YYYY` (Indonesian day-first convention); anything else returns `null`. This is a **separate, small
    module from FN-14a's relative-date parser** — FN-14a resolves phrases like `kemarin`; this resolves literal
    date-formatted cells, a different problem.
  - Reuses `parseMoneyAmount` from `src/lib/shared/money-parse.ts` (FN-14a) for every `amountText` — never a
    second amount tokenizer; a cell that fails to parse produces `'unparseable_amount'`.
- **`src/lib/server/imports/`** (new):
  - `repo.ts` — `createImportBatch(db, spaceId, input)`, `listImportBatches(db, spaceId)`, `undoImportBatch(db,
    spaceId, batchId, expectedUpdatedAt)` (tombstones every `transactions` row with that `import_batch_id` and
    sets `import_batches.undone_at`, in one `db.batch`).
  - `csv-import.ts` — `importCsv(db, spaceId, { fileText, format, defaultWalletId })`: **re-parses the raw text
    from scratch** using the exact same `src/lib/shared/csv.ts` functions the client used for its preview (never
    trusts a client-computed row list for money, same posture `CLAUDE.md` requires for synced records); for each
    mapped row, finds-or-creates its category (by name, matching `kind` to the row's `type`) and wallet (by
    `walletName` falling back to `paymentMethod` when `walletName` is empty, falling back to `defaultWalletId`
    when both are empty), computes `dedupeKey = `${fileHash}:${rowIndex}`` (SHA-256 of the raw file text, hex,
    truncated — the checklist's own named pattern, "file hash + row index,"
    `docs/ENGINEERING_CHECKLIST.md:42`), and calls `createTransaction(db, spaceId, input, { source: 'csv',
    dedupeKey })`; a row whose `dedupeKey` collides with an existing one (the partial unique index, reused as-is

    imported," not retried, not erroring the whole batch. Processed inside `db.batch` calls bounded by Owner
    decision B's row cap.
  - `csv-export.ts` — `exportTransactionsCsv(db, spaceId, fromDate, toDate): string`: reuses FN-05's
    `periodTotals`/`listTransactionsByDay`-family query shape (reading, not duplicating, the aggregate module)
    to fetch every non-transfer, non-deleted transaction in range, renders the template's own column order

    with `=`, `+`, `-`, `@`, a tab, or a carriage return is prefixed with `'` (`docs/ENGINEERING_CHECKLIST.md:67`)
    before RFC 4180 quoting.
  - `validation.ts` — zod for the upload form (`format` enum, `defaultWalletId` optional uuid) and the export

## Out of scope

- **Statement PDF/XLS/screenshot import** (FN-16), **spreadsheet `.xlsx` import** (FN-17) — this feature ships
  `import_batches` and the find-or-create wallet/category helpers those features will reuse, it does not build
  their own readers.
- **Guest/offline save.** CSV *parsing* for the instant preview runs client-side and works without a session
  (matching the mirror's "works... offline" framing for that half); the actual import write still requires a
  signed-in session and a space this pass (Owner decision A) — no IndexedDB write queue exists yet (FN-02).
- **Cross-file "looks like a duplicate" review.** This feature's only duplicate protection is exact-file-replay
  idempotency (`dedupeKey = fileHash:rowIndex`, criterion 19); it never flags "same amount, different file,
  maybe the same purchase" the way FN-16's statement-import review screen will — the mirror's own CSV line says
  "saved directly (no review)," unlike FN-16's "Tinjau impor" (Owner decision A).
- **Multi-tag support.** The CSV template's `tag` column is a single plain-text field on `transactions`, not the
  richer many-to-many `tags`/`transaction_tags` tables named in `docs/ARCHITECTURE.md`'s full data model (Owner
  decision C).
- **Foreign-currency rows.** A Money Manager row whose `Currency` is not `IDR` is skipped with a count, never
  converted or guessed (Owner decision D; FX is FN-05's territory, not built here).
- **Editing `payment_method`/`recurrence`/`tag`/`reference` from the manual compose/edit forms.** This feature
  writes those four new nullable columns directly via `csv-import.ts`; FN-05's `/riwayat/baru`/`/riwayat/[id]/edit`
  forms are not extended to show or edit them this pass — a CSV-imported transaction's extra fields are stored
  correctly and round-trip on export, but are only visible through export, not through the manual edit UI yet.
- **Any row-level editing before import** (no "fix this row's category before saving" step) — fix mistakes after
  the fact in Riwayat, or undo the whole batch and re-import a corrected file.

## Acceptance criteria

**Parsing (`src/lib/shared/csv.ts`)**

1. `parseCsv` correctly splits a comma-delimited file and, separately, a semicolon-delimited file with the same
   logical content, auto-detected from the header row — no manual delimiter selection needed for either.
2. `parseCsv` correctly reads a quoted field containing an embedded comma (e.g. `"Toko, Serba Ada"`) as one field,
   not two, and a quoted field containing an embedded newline as one multi-line field.
3. `detectCsvFormat` returns `'template'` for a header matching `date, type, merchant, amount, currency, category,
   payment_method, recurrence, tag, notes, wallet_source, reference` (case-insensitive, any subset containing at
   least the minimum `date, type, merchant, amount`); `'money_manager'` for a header matching `Period, Accounts,
   Category, Note, Income/Expense, Amount, Currency`; `null` for neither.
4. `mapTemplateRow` on a row with `type = 'transfer'` (or any value outside `expense`/`income`/`pemasukan`)
   returns `'transfer'`/a skip reason — never written as a transaction (`docs/FEATURES.md:184`: "transfer rows
   skipped").
5. `mapTemplateRow` on a row with an empty `wallet_source` falls back to that row's `payment_method` value
   (`docs/FEATURES.md:185`: "empty `wallet_source` falls back to `payment_method`").
6. `mapTemplateRow`/`mapMoneyManagerRow` on a row missing `date` or `amount` (the two fields with no fallback)
   returns the corresponding skip reason — never a row written with a guessed date or amount.
7. `mapMoneyManagerRow` on `Category = "Food/Groceries"` maps to category name `"Food"` (the part before `/`,
   `docs/FEATURES.md:186`); `Note` maps to `title`; `Income/Expense` maps to `type`.
8. `parseCsvDate('2026-10-01')` → `'2026-10-01'`; `parseCsvDate('01/10/2026')` → `'2026-10-01'` (day-first);
   `parseCsvDate('not a date')` → `null`.
9. Every amount cell vector from `docs/FEATURES.md:180` (`"28000"`, `"28.000"`, `"Rp 28.000,00"`) parses via the
   reused `parseMoneyAmount` (FN-14a) to the correct `amount_minor`; this feature adds no second amount parser —
   a code-search in the hand-off shows exactly one call site per mapper.
10. A file whose header matches neither format shows "Format tidak terdeteksi, pilih manual" (and English) and
    the manual format `Segmented` override, rather than silently guessing one.

**Import, idempotency and missing-row handling**

11. Given a `template`-format file naming a category or wallet that does not yet exist in the space, when
    imported, then a new `categories` row (matching `kind`) and/or `wallets` row (`type: 'lainnya'`) is created
    automatically (`docs/FEATURES.md:181`: "missing categories, wallets and tags are created") — never rejected
    for an unknown name.
12. Given the exact same file is uploaded and imported twice, when the second import runs, then every row's
    `dedupeKey` (`fileHash:rowIndex`) collides with the first import's rows via the reused partial unique index;
    the second import's result reports every one of them as "already imported," creates zero new transaction
    rows, and does not error the request.
13. Given a file containing one row with an unparseable amount among otherwise-valid rows, when imported, then
    every valid row still saves and the invalid one is counted and reported, never blocking the rest of the file
    (consistent with the mirror's no-review, best-effort posture — but never a guessed amount for the bad row).
14. Given a `money_manager`-format file with a non-`IDR` `Currency` value on some rows, when imported, then those
    rows are skipped and counted separately from the import's other skip reasons; `IDR` rows in the same file
    still import correctly (Owner decision D).
15. Given any import, when it finishes, then the response shows `trf('Diimpor {imported} · Dilewati {skipped} ·
    Sudah pernah diimpor {already}', …)` (and English), computed from the server's own counts — never a
    client-side re-count of what it thinks it uploaded.
16. Every imported row's `transactions.import_batch_id` is set to the new `import_batches.id`, and every imported
    row's `transactions.source = 'csv'`.
17. Given more rows than the bounded per-request cap (Owner decision B), when imported, then only the cap is
    processed in that request's `db.batch` and the result states how many rows remain unprocessed with guidance
    to split the file — never one unbounded batch (checklist › Data access › "Bounded work").
18. Given a crafted `defaultWalletId` naming a wallet from a different space, when the import action runs, then
    it is refused with the uniform not-found/forbidden response of `requireSpaceAccess`/FN-04's own id check —
    never a 500, never a row against another space's wallet.
19. The server-side `importCsv` call re-parses the raw uploaded text from scratch using the identical shared
    `csv.ts` functions the client used for its preview — it never accepts a client-computed row list as the
    source of truth for amounts or dates (checklist › Sync and account key › "One validator").

**Undo**

20. Given a past, not-yet-undone `import_batches` row, "Urungkan" tombstones every `transactions` row with that
    `import_batch_id` and sets `import_batches.undone_at`, in one `db.batch`; the transactions disappear from
    Riwayat and every total immediately after the server confirms.
21. Given a batch already undone, a second "Urungkan" submission (stale double-click or crafted replay) is a
    no-op — it never tombstones anything twice or errors.

**Export**

22. Given a `from`/`to` date range, `/impor/ekspor` returns a CSV using the template's own column order
    (`docs/FEATURES.md:184`), excluding every transfer-type transaction.
23. Given a transaction whose `title`/`note`/`tag`/`reference` begins with `=`, `+`, `-`, `@`, a tab, or a
    carriage return, when exported, then that cell is prefixed with `'` before RFC 4180 quoting — a regression
    test exports a fixture row with each of the six vectors and asserts every one is neutralised (checklist ›
    "CSV export").
24. Given no `from`/`to` params, `/impor/ekspor` answers a clear validation error, never an unbounded full-history
    export; given a range wider than a bounded cap (Owner decision B's export cap), it is truncated with a note
    rather than scanning unboundedly.
25. Given a template-exported CSV is re-imported into an empty space, when imported, then the resulting
    transactions' amounts, dates, types and titles are identical to the originals that were exported (a
    round-trip fixture test, proving the export and import column mappings agree with each other exactly).
26. Given `/impor/ekspor` is requested with JavaScript disabled, then it still works as a normal GET-triggered
    browser download (checklist › pre-handoff "No-JS forms" — the export link is a plain `<a>`, not a JS-only
    action).

**Cross-cutting (engineering checklist, every item that applies to this feature)**

27. Every load and action under `/impor` resolves the space through `requireSpaceAccess` using
    `event.locals.user` — never a client-supplied `spaceId`.
28. A pre-handoff cross-space probe (crawl `/impor`, `/impor/ekspor`, and every action, as a non-member and as a
    removed member of a space owning a batch/wallet/category id) returns nothing and never 200s.
29. A pre-handoff concurrency probe (20 concurrent imports of the same file) ends with each row created exactly
    once (per criterion 12's dedupe guarantee), never a double-insert, never a 500.
30. Every form body/upload on every action in this feature is read within a size cap (Owner decision B) and
    answers 400 or 415, never 500, on a malformed or oversized file.
31. `{#each}` lists (batch rows, preview summary rows) key by `importBatch.id`, never by filename or title.
32. Every Indonesian phrase added for this feature has an English entry in `i18n-en.ts`; `npm run test`
    (`src/lib/shared/i18n.test.ts`) fails if one is missing.
33. Currency display uses `formatMoney`/`formatMoneyCompact` (`src/lib/shared/money-format.ts:36,62`); dates
    shown convert to/from WIB through `src/lib/shared/dates.ts`.
34. Raw CSV file bytes are processed in the Worker's request handling and never written to R2, D1, or a log;
    only the derived `transactions` rows and the `import_batches` summary row persist — a grep in the hand-off
    confirms no write of raw file text outside that one request's processing.
35. User-facing error text in this feature never contains a file path, stack trace, row id or internal
    identifier.
36. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression test
    (both format mappers, idempotent re-import, formula-injection export, round-trip, bounded-row-cap,

## Owner decisions

**Every decision below is auto-accepted per owner instruction 2026-10-08 ("just auto accept your recomm"). No
open questions remain.**

- **A. Parsing is client-side and account-free (matching the mirror); saving still requires a signed-in session
  this pass.** *Trade-off:* a guest can preview a CSV file's shape before signing up, but cannot actually import
  it until FN-02 ships local-first storage — flagged, not silently claimed done, same as every other Phase 2 PRD
  in this batch.
- **B. Bounded caps:** 5 MB / 5,000 rows per import request (processed in bounded `db.batch` calls), and export
  limited to a one-year range per request. *Trade-off:* an unusually large historical CSV needs splitting into
  multiple files, and a multi-year export needs several requests; both are reasonable bounds for CSV realistically
  produced by a bank or Money Manager and keep every query within D1's practical limits (checklist › "Bounded
  work").
- **C. A single plain-text `tag` column, not the richer many-to-many `tags`/`transaction_tags` tables.**
  *Trade-off:* no multi-tag support until a later feature needs it; the CSV template's own column list only ever
  had one `tag` field, so no mirrored capability is lost.
- **D. Non-IDR rows (Money Manager's `Currency` column) are skipped with a count, never converted or guessed.**
  *Trade-off:* a user with foreign-currency history in Money Manager cannot import those specific rows until FX
  support exists (FN-05/FN-16 territory); every IDR row in the same file still imports correctly.
- **E. Export is a plain GET endpoint (`/impor/ekspor`), not a form action.** *Trade-off:* none meaningful — this
  is the only shape that degrades to a normal browser download without JavaScript and lets the browser's native
  download handling apply.
- **F. No cross-file "maybe a duplicate" review UI — only exact-file-replay idempotency.** *Trade-off:* two
  different CSV exports covering an overlapping date range will double-count overlapping transactions; the user
  fixes this with "Urungkan" on one of the two batches. The mirror's own CSV line says "saved directly (no
  review)," unlike FN-16's heavier statement-import flow, so adding a duplicate-review step here would exceed
  what this pass is asked to build.
