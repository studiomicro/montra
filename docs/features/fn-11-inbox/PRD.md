## Goal

The main journey eventually depends on captured payments landing somewhere a user reviews before they count as
real transactions — FEATURES.md is explicit that Gmail payments, Slack messages and any AI capture needing review
all wait in one place (`docs/FEATURES.md:101-103`). Without FN-11, every later capture feature (FN-14 onward) would
have to invent its own "pending row, pick a category, pick a wallet, save" flow, each slightly different, each
re-implementing the same validation FN-05 already owns. FN-11 is that one shared waiting room and its one shared
"turn this into a real transaction" button, built now — against fictional seeded rows — so FN-14/15/16/17/18/19/29
only ever need to insert a `drafts` row in the shape this feature already defines, never a parallel review UI.

  category/wallet and "Simpan N transaksi" (`docs/FEATURES.md:101-103`); richer per-row editing belongs to each

- Transfer-type drafts. No mirrored capture source ever produces a transfer; `drafts.type` only allows
  `'expense'`/`'income'`.
- Undo after "Simpan" converts a draft into a transaction — once saved, it is a normal `transactions` row and
  FN-05's existing edit/delete flow applies; there is no drafts-specific undo.
- Push or e-mail notification of new drafts arriving (FN-13/FN-24; no notification system to hook into yet).
- Credits or plan gating on how many drafts can be reviewed or saved (FN-30 billing does not exist).
- Sync (IndexedDB) of the `drafts` table — out of scope per the storage decision carried from every Phase 0/1
  PRD; `seq` exists in the schema for later sync but nothing reads or writes it outside the server this pass.

## Acceptance criteria

**Drafts inbox list (`/kotak-masuk`)**

1. Given a space with pending (non-deleted) drafts, when `/kotak-masuk` loads, then every draft for
   `locals.space.id` appears grouped by day (via `occurred_on`, the same WIB bucketing `src/lib/shared/dates.ts`
   gives every other money screen), each row showing its amount via `formatMoney`, its title, a source `Chip`, a
   "Perlu dilengkapi" tag when `wallet_id` or `category_id` is null, and a "Mungkin duplikat" badge when `flag =
   'duplicate'`; the header reads `trf('{n} draf menunggu', …)` (and English).
2. Given no pending drafts, when `/kotak-masuk` loads, then an `EmptyState` shows "Tidak ada draf yang menunggu."
   (and English) and the "Periksa draf" entry is not rendered as an active link.
3. Given the load is in flight, skeleton rows show in place of the list; given the load throws, `ErrorState` with
   retry renders — never an unhandled 500.
4. Given `devRoutesEnabled` is false (any deployed environment without `DEV_ROUTES=1`), when `/kotak-masuk` loads
   or its dev actions are posted directly, then the dev-seed/dev-clear buttons are absent from the rendered page
   and the actions themselves answer 404 — identical to `/dev/ui`'s own gate
   (`src/routes/(app)/dev/ui/+page.server.ts:7-9`); this is never reachable in production.
5. Given `devRoutesEnabled` is true and "Tambah draf contoh" is submitted, then 3–5 fictional `drafts` rows are
   inserted for the current space with `is_demo = 1`, spanning both types, with at least one "ready to save", one
   "needs setup", and one `flag = 'duplicate'`, each badged "Data demo" in the UI and each using a WIB date from
   `src/lib/shared/dates.ts`; "Kosongkan draf contoh" tombstones every `is_demo = 1` row in the space.
6. Given "Abaikan" on a single draft with its confirm step submitted, then `deleted_at` is set (tombstone,
   content-free per `CLAUDE.md`) and the row disappears from the inbox immediately after the server confirms.

**Review screen (`/kotak-masuk/periksa`)**

7. Given at least one pending draft, when "Periksa draf" is opened, then every pending draft appears pre-selected
   in a checkbox `GroupList`, with a running "{n} dipilih" count and "Pilih semua"/"Kosongkan pilihan" controls.
8. Given a selection containing both `type = 'expense'` and `type = 'income'` drafts, when "Atur kategori" is
   opened, then it is refused with "Pilih draf dengan jenis yang sama untuk mengatur kategori sekaligus" (and
   English) and no category sheet opens — a mixed-type selection is never partially or silently applied (Owner
   decision A).
9. Given a selection that is entirely one `type`, when "Atur kategori" is submitted with a category of the
   matching `kind`, then every selected draft's `category_id` is updated in one `db.batch`, the sheet closes, and
   the rows reflect the change without a page reload.
10. Given any selection (mixed or single type), when "Atur dompet" is submitted with a wallet belonging to the
    current space, then every selected draft's `wallet_id` is updated in one `db.batch` regardless of `type`
    (wallets carry no kind restriction).
11. Given a wallet or category id from a different space (crafted request), when "Atur dompet"/"Atur kategori"
    is submitted, then rows naming that id are silently excluded from the update — the server resolves "drafts
    belonging to `locals.space.id`" itself, so a foreign id has nothing to match (no existence oracle, no 500);
    the action's result states how many of the selection were actually updated.
12. Given a selection where every selected draft already has both `wallet_id` and `category_id` set, when
    "Simpan N transaksi" is submitted, then each one is validated through FN-05's existing create-transaction zod
    schema (never a second schema) and `createTransaction(db, spaceId, input, { source: draft.source, dedupeKey:
    draft.dedupeKey })` is called once per draft; each new `transactions` row carries that draft's original
    `source` and `dedupe_key`; each saved draft is tombstoned with `saved_transaction_id` set to the new row's
    id; the page returns to `/kotak-masuk` showing "Disimpan {n} transaksi" (and English) — shown only after the
    server confirms every write, never optimistically.
13. Given a selection where some drafts are missing `wallet_id` or `category_id`, when "Simpan N transaksi" is
    submitted, then the complete ones save as in criterion 12 and the incomplete ones remain, unchanged, in the
    inbox; the response reads `trf('Disimpan {saved} dari {total} transaksi · {incomplete} belum lengkap', …)`
    (and English) — one incomplete row never blocks the rest of the batch (Owner decision B).
14. Given more than 50 drafts selected in one submission (the same bounded page size Riwayat's own default uses,
    `docs/features/fn-05-transactions/PRD.md:427-429`), when "Simpan N transaksi" is submitted, then at most 50
    are processed in that request's `db.batch` and the result states how many remain for a further submission —
    never one unbounded batch (checklist › Data access › "Bounded work").
15. Given the same draft id appears twice in one posted selection (duplicate checkbox value, crafted or
    double-submitted), when the save action runs, then it is de-duplicated before use and processed exactly
    once — never two transactions created from one draft.
16. Given a draft already tombstoned by a previous save (`saved_transaction_id` set), when any action targets
    its id again (crafted replay or a stale double-submit), then it is treated as not found by every query in
    this feature — the inbox never creates a second transaction from an already-saved draft.
17. Given "Abaikan" discards a draft whose `dedupe_key` is not null, then the partial unique index described in
    Architecture notes still blocks any future row (real capture or another discard attempt) from reusing that
    exact `(space_id, source, dedupe_key)` combination — a discarded captured draft is never recreated from the
    same source (`CLAUDE.md` › Data and runtime conventions), even though no real capture exists yet to prove it
    with a live writer; the regression test inserts a second row with the same key directly and asserts the
    `INSERT` is rejected.

**Money and dates**

18. Every amount in this feature renders through `formatMoney`/`formatMoneyCompact`
    (`src/lib/shared/money-format.ts:36,62`); no hand-built `Rp` string.
19. A draft's `occurred_on`/`occurred_at` are copied verbatim onto the transaction it becomes — this feature
    never recomputes or re-buckets a date; the only dates it creates itself (the dev seed) go through
    `wibTodayString()`/`wibDateString()` (`src/lib/shared/dates.ts`), never a hand-rolled string.

**Cross-cutting (engineering checklist, every item that applies to this feature)**

20. Every load and action under `/kotak-masuk` and `/kotak-masuk/periksa` resolves the space through
    `locals.space.id` — no route or form field is trusted as a space id; every draft, wallet and category id
    accepted from a client request is re-checked against that space before use (criterion 11).
21. A pre-handoff cross-space probe (crawl both routes and every action as a non-member and as a removed member
    of the space owning a given draft id) returns nothing and never 200s.
22. A pre-handoff concurrency probe (20 concurrent "Simpan" submissions over an overlapping selection) ends with
    each draft saved exactly once, never two transactions from one draft, never a 500.
23. Every form body on every action in this feature is read within a size cap and answers 400 or 415, never 500,
    on a malformed or oversized body (reuse FN-01's `src/lib/server/forms.ts` guard, not a new one).
24. `{#each}` lists (day groups, draft rows) key by `draft.id`, never by title or merchant text.
25. Every Indonesian phrase added for this feature has an English entry in `i18n-en.ts`; `npm run test`
    (`src/lib/shared/i18n.test.ts`) fails if one is missing.
26. Focus returns to the opener when any `Sheet` in this feature closes; touch targets ≥ 44 px (including the
    new checkbox row); WCAG AA contrast in both themes (FN-00 token system, no new colours).
27. User-facing error text in this feature never contains a file path, stack trace, row id or internal
    identifier.
28. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression test
    (dedupe-key-survives-discard, mixed-type category refusal, 50-row bulk-save bound, duplicate-id
    de-duplication, already-saved-draft replay, cross-space probe) is shown failing on the unfixed code first
    (checklist › Tests › "Fail-before proof").

## Architecture notes

**Modules touched / added**

- `src/lib/server/db/schema.ts` — add one table (Drizzle), migration generated into `migrations/0007_drafts.sql`:
  - `drafts (id pk text, space_id text not null references spaces.id, type text not null check(type in
    ('expense','income')), amount_minor integer not null check(amount_minor > 0), currency text not null default
    'IDR', title text, note text, category_id text references categories.id, wallet_id text references
    wallets.id, occurred_on text not null, occurred_at integer not null, source text not null check(source in
    ('gmail','voice','receipt','statement','spreadsheet','csv','slack')), dedupe_key text, flag text check(flag
    in ('duplicate','needs_review')), is_demo integer not null default 0, saved_transaction_id text references
    transactions.id, created_at integer not null, updated_at integer not null, deleted_at integer, seq integer
    not null)`. Index `(space_id, deleted_at, created_at)` for the list query. A **partial unique index**
    `(space_id, source, dedupe_key) WHERE dedupe_key IS NOT NULL` — deliberately with no `deleted_at` condition,
    mirroring FN-05's own `transactions` index exactly (`docs/features/fn-05-transactions/PRD.md:338-341`), so a
    discarded or already-saved draft permanently blocks a re-insert with the same source and dedupe key.
  - `seq` assignment — reuse whatever shared `nextSeq(db, spaceId)` helper FN-03/FN-04/FN-05 landed by the time
    this feature is implemented; do not invent a third counter mechanism (same precedent every prior PRD states).
- `src/lib/server/drafts/` — new, as described in Scope.
- `src/lib/server/transactions/repo.ts#createTransaction` — **extended, not duplicated**: add the optional
  fourth argument described in Scope; every FN-05 call site (`/riwayat/baru`, `/riwayat/[id]/edit`) keeps calling
  it with no fourth argument and gets the unchanged `{ source: 'manual', dedupeKey: null }` default.
- `src/lib/server/transactions/validation.ts` — its existing create-transaction zod schema is imported by
  `src/lib/server/drafts/repo.ts` to validate a draft's fields before `createTransaction` is called; no second
  schema is written for the same shape.
- `src/routes/(app)/kotak-masuk/`, `/kotak-masuk/periksa/` — new trees, as described in Scope; replaces the
  `[stub=stub]` rendering for the `kotak-masuk` slug (`src/params/stub.ts:1` loses that entry from `SLUGS`, the
  same pattern FN-01/FN-03 used for their own slugs).
- `src/lib/ui/kit/GroupRow.svelte` — the small, scoped `selected`/`onToggle` prop addition described in Scope;
  no new component, no change to any other call site's current rendering.
- `src/lib/server/dev.ts` (`devRoutesEnabled`) — reused unchanged to gate the two dev-only actions, exactly as
  `src/routes/(app)/dev/ui/+page.server.ts` and `src/routes/api/v1/dev/ping/+server.ts` already do.
- `src/lib/shared/dates.ts` (`wibTodayString`, `wibDateString`) and `src/lib/shared/money-format.ts`
  (`formatMoney`, `formatMoneyCompact`) — reused unchanged; FN-11 adds no date or money logic of its own.
- `src/lib/shared/i18n.ts`/`i18n-en.ts` — add every new phrase.
- `test/helpers/d1.ts` (`withLocalD1`) — reused unchanged for Vitest coverage of `repo.ts` against a real local
  D1 with the migration applied.
- Worker: app Worker only (SSR, loaders, actions) — no `workers/jobs`/`workers/inbound` involvement; this pass
  writes no row with a real (non-demo) provenance, so nothing here calls out to AI Gateway or any Queue.

**Reuse / do not duplicate**

- One call to `locals.space.id` resolution per load/action, no second authorization path.
- `createTransaction` and its zod schema are the **only** way a draft becomes a transaction — FN-11 does not

## Owner decisions

**Every decision below is auto-accepted per owner instruction 2026-10-08 ("just auto accept your recomm"). No
open questions remain.**

- **A. Mixed-type bulk category selection.** *Proposed default (auto-accepted per owner instruction 2026-10-08):*
  refuse the whole "Atur kategori" action when the selection mixes `expense` and `income` drafts, rather than
  silently applying it to the matching subset. *Trade-off:* a user reviewing a mixed batch must split the
  selection into two "Atur kategori" calls (one per type); the alternative — applying only to the matching rows
  and skipping the rest — risks the user not noticing some rows were quietly left uncategorised.
- **B. Incomplete drafts on "Simpan".** *Proposed default (auto-accepted per owner instruction 2026-10-08):*
  save every selected draft that already has both `wallet_id` and `category_id`, leave the rest untouched in the
  inbox, and report both counts (criterion 13), rather than blocking the entire batch until every row is
  complete. *Trade-off:* a user must re-open the inbox to find which specific drafts still need a wallet/category
  if they do not read the summary line carefully; the alternative (all-or-nothing) is safer but adds friction to
  an otherwise-ready batch for the sake of one stray row.
- **C. Bulk-save page size.** *Proposed default (auto-accepted per owner instruction 2026-10-08):* 50 drafts per
  "Simpan" request, matching Riwayat's own page-size default, cursor-free (criterion 14). *Trade-off:* a very
  large look-back import (hundreds of drafts, once FN-19 ships) needs several submissions; the alternative (one
  unbounded batch) is exactly what the checklist's "bounded work" rule forbids.
- **D. Dev-seed data shape.** *Proposed default (auto-accepted per owner instruction 2026-10-08):* fictional,
  additive on every click, spanning both types, including one "ready", one "needs setup" and one
  duplicate-flagged row (criterion 5). *Trade-off:* none real — this is a test fixture, badged "Data demo" and
  never counted as a working capture path per `CLAUDE.md` › Verification ("fixtures... never count as a working
  capture path").
