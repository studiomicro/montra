## Goal

The main journey ends at "see safe-to-spend" and "ask the assistant", but comparable apps' feature sets — and a
household manager's actual question — goes one step further: "am I going to make it to Rp 1.250.000 for the trip
in March?" FN-10 gives a space a short list of named savings targets, each with a target amount and an honest
progress figure built the same way every other balance in this app is built: not a single number someone can
silently edit, but the sum of a small, reversible log of contributions — mirroring the precedent FN-04/FN-05
already set for wallet balances (`opening_balance_minor + Σ transactions`, never a directly-editable "current
balance" field). A goal's "saved" amount is a user-declared tracking figure, never a wallet transfer or a real
movement of money — `CLAUDE.md` is explicit that MONTRA "does not hold funds or move money," so logging a
contribution to a goal updates nothing about any wallet's balance; it is bookkeeping intent, not a transaction.

## Out of scope

- Linking a goal to a wallet or to real transactions in any way — a contribution is a standalone log entry, never
  a transfer, never a transaction, never a change to any `wallets` balance (`CLAUDE.md` › Product boundaries:
  "not a bank … no funds held, no money moved"). A later feature that wants "automatically mark Rp 50.000 of my
  savings-wallet balance as progress toward this goal" would need its own, separately-scoped design — not built
  here, and this schema does not assume it will ever exist.
- Negative contributions / withdrawals as a first-class action (Owner decision B) — the only way to reduce a
  goal's saved amount is to delete a previously-logged contribution (tombstone, reversible); there is no
  "subtract Rp X" form field.
- Hard delete of a goal or a contribution — both are tombstones (`deleted_at`), never a hard `DELETE`, matching
  every other user-data table in this codebase.
- Reordering goals, goal categories/icons, goal photos, or a progress notification ("you're 80% there!" —
  that belongs with FN-24's notification system, which does not exist yet).
- Several currencies per goal or FX conversion on a contribution — a goal's `currency` (default `IDR`) is fixed
  at creation; every contribution to it is assumed the same currency, no independent currency field, mirroring
  FN-05's own deferred-FX decision for transactions.
- Pagination of the goals list itself beyond the 50-row cap (Owner decision C) — no "load more" on `/kekayaan`'s
  Tabungan section this pass.
- A dedicated `/kekayaan` sub-navigation (tabs/segmented switcher between Dompet/Tabungan/future sections) — this
  feature adds one more stacked `GroupList` section to the single-page layout FN-04 already has; the real
  sub-navigation restructuring FN-04's own PRD flagged is deferred again, to whichever of FN-25/26/27/28 lands
  next and finally makes the page too long for stacked sections (Owner decision D).
- Sharing a specific goal with only some space members, or goal-level permissions — a goal is visible and
  editable by every member of the space exactly like a wallet or a budget (`docs/FEATURES.md:97`: "shared with
  the space"), no per-goal role.

## Acceptance criteria

**Create a goal (`createGoal` action on `/kekayaan`)**

1. Given the "+ Tambah target" sheet with a name (1–60 chars) and a positive target amount, when submitted, then
   one `goals` row is written (`space_id = locals.space.id`, `target_amount_minor` via `digitsToMinor`, never
   `parseFloat`, `currency = 'IDR'` default), the sheet closes, and the new goal appears in the Tabungan section
   at `0%` / `Rp 0 / {target}` without a page reload.
2. Given the same goal, when the page is reloaded (full refresh), then it is still present with the same figures
   — persisted state survives reload.
3. Given a name containing control or zero-width characters or exceeding 60 characters, or a target amount of
   zero, blank, negative, or non-numeric, when submitted, then the action fails with a field error (`tr()`/
   English) and no row is written (checklist › Access and privacy › "Untrusted text"; checklist › Money and
   dates › "Integers only").
4. Given JavaScript is disabled, when the create-goal form is submitted, then it still works as a normal form
   POST (progressive enhancement, checklist › Tests › pre-handoff "No-JS forms").

**Goal progress (the FN-10 "Mirror" line: `docs/FEATURES.md:96-97`, e.g. "Tabungan 100 % · Rp 1.250.000 /
Rp 1.250.000")**

5. Given a goal with `targetAmountMinor = T` and zero or more non-deleted contributions summing to `S`
   (`goalSavedMinor`), when its progress renders anywhere (the Tabungan section row or the detail page header),
   then it shows exactly `formatMoneyCompact(S) + ' / ' + formatMoneyCompact(T)` and `floor(S * 100 / T) + '%'`
   — both figures computed by `goalSavedMinor`/`goalProgressPercent`, never a client-side re-sum of the
   contribution list and never a separately stored "current saved" column (checklist › Money and dates ›
   "Totals reconcile": a unit test asserts the shown percent equals the manual sum of seeded fixture
   contributions, for the one function every render of this figure must call).
6. Given `S >= T` (goal met or exceeded), when it renders, then a "Tercapai" badge/style shows in addition to the
   percent (which may read over 100%, e.g. "108%" — never silently capped in the text, only the `ProgressBar`'s
   visual fill is capped at 100% width).
7. Given a goal with zero contributions, when it renders, then it shows `Rp 0 / {target}` and `0%` — an honest
   zero, never hidden, matching the same "money is never invented, never hidden" posture Beranda/FN-07 already
   take toward a zero figure.

**Log a contribution (`addContribution` action on `/kekayaan/tabungan/[id]`)**

8. Given the "Tambah tabungan" sheet with a positive amount and an optional note, when submitted, then one
   `goal_contributions` row is written (`goal_id`, `space_id`, `amount_minor > 0` enforced by both validation and
   a SQL `CHECK`, `created_by_user_id = locals.user.id`), the sheet closes, and the goal's progress (saved
   amount, percent, `ProgressBar` width) updates on the page only after the server confirms the write — no
   optimistic figure.
9. Given an amount of zero, blank, negative, or non-numeric, when submitted, then the action fails with a field
   error and no row is written — contributions are never negative (Owner decision B: the only subtraction path
   is deleting a logged contribution, criterion 11).
10. Given the reload happens (full page refresh) after a contribution is saved, then it and the updated progress
    figures are still present.

**Delete a contribution (`deleteContribution` action)**

11. Given "Hapus" on a logged contribution (with a confirm step), when submitted, then `deleted_at` is set
    (tombstone, content-free per `CLAUDE.md`), the row disappears from the contribution history list, and the
    goal's saved amount/percent recompute immediately (lower) after the server confirms — reversing a mistaken
    contribution is the only way this feature allows the saved figure to decrease.
12. Given a contribution id that belongs to a different goal or a different space (crafted request), when the
    delete action runs, then it is refused with the uniform not-found response (no row changes) — the query is
    always scoped by both `space_id` and `goal_id`, never by the contribution id alone.

**Edit and archive a goal (`updateGoal`, `archiveGoal`, `restoreGoal` actions)**

13. Given a goal opened for edit (name and/or target amount changed) and submitted with the `updated_at` the
    detail page loaded, then the row updates (`updated_at` advances) and the new name/target render only after
    the server confirms.
14. Given two tabs open the same goal for edit with the same stale `updated_at` (pre-handoff "two tabs / stale
    forms" probe), when both submit, then the second is refused with "Berubah sejak terakhir dimuat" (and
    English) — the exact phrase FN-04 already uses, not a re-keyed duplicate.
15. Given "Arsipkan" on a goal with existing contributions, when submitted, then the `goals` row is tombstoned
    (`deleted_at` set), it disappears from `/kekayaan`'s Tabungan section and from `/kekayaan/tabungan/[id]`'s
    normal view, but its `goal_contributions` rows are left untouched (not tombstoned) so "Pulihkan" later
    restores the exact same progress, never a data loss on archive.
16. Given "Pulihkan" on an archived goal, when submitted, then `deleted_at` is cleared and it reappears with its
    original progress figures intact (archiving/restoring a goal never touches its contribution log).

**Cross-cutting (engineering checklist, every item that applies to this feature)**

17. Every `+page.server.ts` load and action under `/kekayaan` (the Tabungan section) and
    `/kekayaan/tabungan/[id]` resolves the space through `event.locals.space.id`; the `[id]` routes additionally
    scope every goal/contribution lookup by `WHERE space_id = ? AND id = ?` in the same query — never a
    client-supplied `spaceId`, and a goal or contribution id from a different space gets the identical
    not-found response as a missing id (no existence oracle).
18. A pre-handoff cross-space probe (crawl every route and action in this feature as a non-member and as a
    removed member of the space that owns a given goal/contribution id) returns nothing and never 200s.
19. A pre-handoff concurrency probe (20 concurrent `addContribution` submissions against the same goal) never
    produces a lost write or a 500 — `goalSavedMinor` is always computed fresh from SQL `SUM()` over the
    contributions table, so there is no separate mutable counter that could race or drift (this is *why* a
    contribution log was chosen over a single mutable "saved" column — see Owner decision B).
20. Every form body on every action in this feature is read within a size cap and answers 400 or 415, never 500,
    on a malformed or oversized body (reuse FN-01's `src/lib/server/forms.ts` guard, not a new one).
21. `{#each}` lists (goal rows, contribution rows) key by `goal.id`/`contribution.id`, never by name or note text.
22. Every Indonesian phrase added for this feature has an English entry in `i18n-en.ts`; `npm run test`
    (`src/lib/shared/i18n.test.ts`) fails if one is missing.
23. Currency display anywhere in this feature uses `formatMoney`/`formatMoneyCompact`
    (`src/lib/shared/money-format.ts:36,62`); no hand-built `Rp` string; every timestamp shown (contribution
    date, "created on") is converted to/from WIB through `src/lib/shared/dates.ts`, never a raw UTC date.
24. Focus returns to the opener when any `Sheet` in this feature closes; touch targets ≥ 44 px, including the new
    `ProgressBar`'s surrounding tappable row; WCAG AA contrast in both themes for the `ProgressBar` fill (reuses
    the existing `--ink`/`--chart-track` tokens, no new colour).
25. User-facing error text in this feature never contains a file path, stack trace, row id, or internal
    identifier.
26. `npm run gates` (check, lint, test, build) is clean on the branch before hand-off; every new regression test
    (contribution-sum totals-reconcile test, 20-way concurrent-contribution probe, stale-`updated_at` edit race,
    cross-space probe, negative/zero amount rejection, archive-then-restore preserves contribution history) is
    shown failing on the unfixed code first (checklist › Tests › "Fail-before proof").

## Owner decisions

**Every trade-off below is auto-accepted per owner instruction 2026-10-08 ("just auto accept your recomm"). No
question in this PRD is left open; the defaults below are the shipped behaviour.**

- **A. Where the goals UI lives.** *Auto-accepted default:* a new "Tabungan" section on the existing `/kekayaan`
  page (list) plus a real sub-route `/kekayaan/tabungan/[id]` (detail, contributions, edit/archive) — not a new
  top-level tab, not a route under `/pengaturan`. *Trade-off:* goals compete for vertical space on `/kekayaan`
  with the wallet list and, eventually, net worth/subscriptions/belongings/collectibles (FN-25–28); this is the
  exact restructuring-deferral FN-04's own PRD already flagged as inevitable, now paid down by one more section
  rather than by building sub-navigation nobody has asked for yet.
- **B. Contribution model: an append-only log summed by SQL, or a single mutable "saved amount" column with an
  increment/decrement action.** *Auto-accepted default:* the log (two tables, `goalSavedMinor` as a grouped
  `SUM()`), mirroring the wallet-balance precedent FN-04/FN-05 already established
  (`docs/features/fn-05-transactions/PRD.md:64-66`). *Trade-off:* this is objectively more schema and one more
  table than the simplest possible version (a single `saved_amount_minor` column on `goals`, updated in place by
  an `UPDATE … SET saved_amount_minor = saved_amount_minor + ?` guarded statement); the log was chosen anyway
  because (a) it gives a real, reversible history for free (criterion 11's "delete a mistaken contribution"
  has nowhere to attach to on a single mutable column without inventing a second, parallel log anyway), (b) it
  removes any read-then-write race on the saved figure under concurrent contributions (criterion 19) without a
  guarded-statement dance, and (c) it is the smallest model consistent with every other balance in this codebase
  already being "opening/base value + a summed log," not a special case. This is the one place this PRD
  deliberately does *not* take the literally smallest possible schema, because the literally smallest one would
  violate the "totals reconcile"/no-silent-drift discipline the rest of the codebase already enforces.
- **C. Goals list cap on `/kekayaan`.** *Auto-accepted default:* 50 active goals per space, no pagination.
  *Trade-off:* a space with more than 50 goals (unlikely for a personal-finance tool) would not see goal #51 on
  this screen; a real cursor-paginated list was judged not worth the extra UI for a count no realistic household
  will reach, matching the same proportionality FN-04 applied to its own unpaginated wallet list.
- **D. `/kekayaan` sub-navigation.** *Auto-accepted default:* still none — Dompet and Tabungan are two stacked
  `GroupList` sections on one page, no tabs/segmented switcher. *Trade-off:* the page gets measurably longer on
  a 360 px phone with both sections populated; acceptable for now, and the real fix (sub-navigation) is
  explicitly left for whichever of FN-25/26/27/28 finally needs it, not invented speculatively here.
- **E. Achieved-goal treatment.** *Auto-accepted default:* an "Tercapai" badge/style once `percent >= 100`, with
  no automatic archiving and no celebratory animation/notification. *Trade-off:* a fully-funded goal just sits in
  the list looking "done" until the user archives it themselves; auto-archiving on reaching 100% was considered
  and rejected because a user might keep contributing past the target (e.g. a buffer), and auto-archiving would
  hide that overflow from the list without being asked to.
